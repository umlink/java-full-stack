# 阶段五 · 小点 4：可观测性体系（Metrics / Logging / Tracing / 告警）

> 所属：阶段五 云原生与运维工程
> 定位：三支柱 + 告警治理，让你**在用户报障之前发现问题**。Metrics 回答「有没有事」、Tracing 回答「慢/错在哪一段」、Logging 回答「那一段里具体发生了什么」——三者靠 TraceID 串成一条线。

## 快速入门

> 本节为「可观测速览」：先认识三大支柱各管什么、解决什么问题；「Prometheus、告警治理」留在正文提高部分。

### 本讲核心关键词速查

| 关键词 | 一句话大白话 | 例子 |
|-|-|-|
| 可观测性 | 让你「看得见系统内部在干嘛」 | 指标、日志、追踪 |
| Metrics（指标） | 数字型度量（QPS/延迟/错误率） | `http_requests_total` |
| Logging（日志） | 文本型事件记录 | 报错日志 |
| Tracing（追踪） | 一次请求跨服务的完整链路 | TraceID 串联 |
| Prometheus | 主流指标采集+存储系统 | 抓取应用指标 |
| Grafana | 指标可视化面板 | 图表、大盘 |
| TraceID | 一次请求的唯一追踪 ID | 日志/追踪关联 |
| 告警 | 指标异常时通知人 | 阈值触发报警 |

### 本讲在解决什么问题

- **问题**：服务崩了/慢了，用户在投诉，你却不知道哪出问题。可观测性三支柱让你**在用户报障前发现**：Metrics 说有故障，Tracing 定位在哪段，Logging 看具体发生了什么。
- **你要带走的一句话**：**Metrics** 回答「有没有事」（数字），**Tracing** 回答「慢/错在哪一段」（链路），**Logging** 回答「那一段里具体发生了什么」（细节）。三者靠同一个 TraceID 串起来。

### 最简可运行示例（照抄能跑）

```yaml
# Prometheus 抓取 Spring Boot 指标(通过 Actuator 暴露)
spring:
  application:
    name: order-service
management:
  endpoints:
    web:
      exposure:
        include: health,metrics,prometheus   # 露出这些端点
  prometheus:
    metrics:
      export:
        enabled: true                        # 打开 Prometheus 导出(注册表专属前缀 management.prometheus.metrics.export)
  endpoint:
    health:
      probes:
        enabled: true                        # 暴露 /actuator/health/liveness|readiness 探针(配合 02-K8s 讲)
```

```bash
# 取一个指标: 看请求延迟(直方图桶是算 p99 的前提)
curl http://localhost:8080/actuator/prometheus | grep http_server_requests
```

> 代码备注（逐行解释）：
> - `include: health,metrics,prometheus`：让 Spring Boot Actuator 暴露这几个端点，Prometheus 从这里抓指标。
> - `curl /actuator/prometheus`：手动取一次指标看看——`http_server_requests` 就是请求数/延迟。
> - 关键点：**要算 p99（99% 请求多快）必须有直方图桶**（`histogram` 配置）——只采平均值算不出分位数（正文展开）。
> - 这就是 Metrics 的采集：应用暴露指标 → Prometheus 抓取 → Grafana 展示。三步让你「看得到有没有事」。

### 关键概念说明

| 概念 | 干什么 | 最易踩的坑 |
|-|-|-|
| Metrics | 数字指标 | 算 p99 必须有直方图桶 |
| Logging | 文本日志 | 用 TraceID 关联，别靠 grep 时间点 |
| Tracing | 跨服务链路 | 需要透传 TraceID（MDC） |
| TraceID | 追踪唯一 ID | 日志/Trace 都带它才能串起来 |
| 告警 | 异常通知 | 别制造告警疲劳（收敛/抑制） |
| RED / USE | 服务/资源双视角 | 服务看 Rate/Errors/Duration |

### 常用约定 / 命名提示

- **排查三步**：先看大盘（Metrics 有没有异常）→ 按 TraceID 看链路（Tracing 在哪段慢）→ 看对应日志（Logging 具体发生了什么）。
- **结构化日志**：用 JSON + TraceID 字段，别只记一句话文本——否则没法按 TraceID 检索。
- **告警三原则**：可执行动作、按症状告警（不是按原因）、收敛抑制防告警疲劳。

## 学习内容详情

### 1. Metrics：从 Actuator 到 Grafana

```yaml
# Spring Boot 侧：暴露 Prometheus 端点（第 2 讲 Micrometer 自动埋点的出口）
management:
  endpoints:
    web:
      exposure:
        include: health, metrics, prometheus    # 只暴露需要的
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true              # ⚠️ 关键: 直方图桶 —— 算 p99 的前提(阶段六第 2 讲呼应)
      slo:
        http.server.requests: 50ms, 100ms, 500ms
```

```text
# Prometheus 拉取模型：定时抓各实例的 /actuator/prometheus
scrape_configs:
  - job_name: order-service
    kubernetes_sd_configs: [...]     # 服务发现: 按 Pod label 抓 —— 复用第 2 讲的「标签选中」机制
    metrics_path: /actuator/prometheus

# Grafana 面板的四条起步查询(黄金信号):
#   流量 QPS:    rate(http_server_requests_seconds_count[5m])
#   错误:        sum by(status) ...{status=~"5.."} / sum ...   → 错误率
#   延迟 p99:    histogram_quantile(0.99, sum by(le) (rate(http_server_requests_seconds_bucket[5m])))
#   饱和度:      jvm_memory_used / max, cpu_usage, 连接池 pending
```

> **p99 是估算出来的**：分位数是 `histogram_quantile` 从直方图桶**插值估算**的，桶越粗 p99 误差越大——设 SLO 阈值前先看桶边界设计（上面 `slo` 那几档就是桶边界）。

- **四大黄金信号**：延迟 / 流量 / 错误 / 饱和度——任何服务先建这四个面板，再谈细分指标。
- **RED / USE**：RED（服务视角：Rate / Errors / Duration）管接口，USE（资源视角：Utilization / Saturation / Errors）管机器——一个面板一套视角，缺一边就有盲区。
- Java 埋点：**Micrometer**（Boot 自带指标门面，JVM / HTTP / 连接池开箱即有）——自定义业务指标用 `Counter` / `Timer`，高基数标签（userId / orderId）**禁止**塞进 label（时间序列爆炸）。

### 2. Logging：ELK / Loki

```json
// 结构化 JSON 日志（logback 配 JSON encoder）——字段化才可查可聚合，杜绝「拼一句话」
{"@timestamp":"2026-09-06T14:30:02.153+08:00","level":"WARN","logger":"c.d.o.OrderService",
 "trace_id":"a3f8c2e1d4","user_id":"1001","order_id":"o-202609060001","stage":"stock-deduct",
 "msg":"库存不足, 进入排队补偿", "amount":299.0}
```

- **ELK**（Elasticsearch + Filebeat/Fluent Bit 采集 + Kibana 查询）：全文索引强，成本也高；**Loki**（Grafana 系）：只索引标签（app / env / trace_id）不索引全文，对象存储后端——便宜十倍的默认选择，中小团队优先。
- **MDC + TraceID 关联**（阶段二第 2 讲落地形态）：logback pattern 输出 `%X{trace_id}`，从 trace_id 一键跳到该请求的全部日志；ELK 查询 `trace_id:"a3f8c2e1"` 替代「grep 时间点对时间」——这就是日志的质变。

### 3. Tracing：OTel / SkyWalking

**分布式追踪**：一次请求跨多服务，把每段工作记成一个 **Span**（带时间 / 父子 / 标签），串成 **Trace**——「慢在哪一段」一眼可见。

```java
// OpenTelemetry(未来事实标准, OTLP 协议统一上报): 业务代码埋一行拿全链上下文
var span = tracer.spanBuilder("order.create").startSpan();
try (var scope = span.makeCurrent()) {          // makeCurrent: 激活后, 嵌套的 HTTP/MQ 调用自动续 span
    span.setAttribute("order.id", order.id());   // 业务标签: 排查时按属性过滤
    return doCreate(cmd);
} catch (Exception e) {
    span.recordException(e); span.setStatus(StatusCode.ERROR); throw e;
} finally { span.end(); }
// HTTP header 透传: traceparent=00-<trace_id>-<span_id>-01 —— 网关/下游自动接续(W3C 传播标准)
```

| 方案 | 定位 | 接入方式 |
|-|-|-|
| **OpenTelemetry** | 规范 + SDK + 协议（统一指标/日志/追踪） | OTel Java Agent 无侵入 + OTLP 上报任意后端 |
| **SkyWalking** | 国内主流 APM，开箱面板 + 告警 | Java Agent 字节码增强，零代码 |
| **Jaeger** | CNCF 追踪后端代表 | OTel 生态兼容 |

- 实践路径：JVM 参数挂 Agent（`-javaagent:otel/... -Dotel.service.name=order-service`）即得自动埋点（HTTP / JDBC / Redis / MQ 客户端全覆盖）；业务只补关键 Span 与属性。
- 三支柱合流：Span 上带 `trace_id` → 日志 JSON 带同一 `trace_id` → 指标异常时按 `trace_id` 钻取——**「大盘报警 → Trace 看哪段慢 → 日志看细节」的三段跳**是可观测的工作流本体。

### 4. 告警：分级与疲劳治理

```yaml
# Alertmanager 路由：按标签分派到不同通道与响应时限
route:
  receiver: im-default
  routes:
    - match: { severity: critical }       # P0: 电话/短信, 5 分钟内响应
      receiver: oncall-phone
      group_wait: 30s                     # 同告警聚合窗口 —— 防风暴刷屏
      repeat_interval: 1h
    - match: { severity: warning }        # P1: IM 群, 当天处理
      receiver: team-im

# Prometheus 告警规则示例：黄金信号的两条起步规则
groups:
  - name: api
    rules:
      - alert: HighErrorRate
        expr: sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
            / sum(rate(http_server_requests_seconds_count[5m])) > 0.01   # 错误率 >1% 持续 5m
        for: 5m
        labels: { severity: critical }
      - alert: LatencyP99High
        expr: histogram_quantile(0.99, sum by(le) (rate(http_server_requests_seconds_bucket[5m]))) > 0.5
        for: 10m
        labels: { severity: warning }
```

- **告警三原则**：① 每条告警必须配可执行动作（没动作就删）；② 按症状告警不按原因（「下单成功率跌 5%」优于「CPU 80%」——后者可能根本不是问题）；③ 收敛与抑制（同一故障派生的告警按服务 / 根因归并成一条）。
- **On-Call 闭环**：告警 → 响应 → 止血（回滚 / 扩容 / 降级，先止血再查因）→ 复盘 → 改进项回写监控——没有闭环的告警系统会退化成「大家都忽略的噪音源」。

### 坑点提醒

- **没有直方图桶就算不了聚合 p99**：`percentiles-histogram` 没开，Grafana 里只有各实例 p99 的「平均值」——数学上错的（阶段六第 2 讲）。
- **高基数标签**：把接口路径带用户 ID、错误 message 塞进 label → Prometheus 内存炸——用日志 / Trace 承载高基数信息，指标只留低基数维度。
- **日志没 JSON 化就接 ELK**：全当大字符串存，查询靠正则——先结构化后接采集器，顺序别反。
- **Trace 采样率一刀切 100%**：全量采集在大流量下成本失控又没人看——错误与慢请求全采（tail-based），正常流量头采样 1%。注意：按结果采样（错误/慢请求全采）需要 OTel Collector 的 tail_sampling 处理器做——应用侧只能做头采样（按比例）。
