# 阶段一 · 小点 3：泛型、反射、注解与动态代理

> 所属：阶段一 Java 语言深化与 JVM 体系
> 定位：这是 Spring / MyBatis 一切「魔法」的底层机制，必须吃透。看不懂这一讲，后面看到 `@Autowired`、`@Transactional`、Mapper 接口无实现类能跑，都只能停留在「很神奇」；看懂了，框架对你就是「可推理的系统」。

## 快速入门

> 本节为「框架魔法解密前置」：先认识这几个让 Spring / MyBatis「看起来很神奇」的底层概念；「PECS 怎么推、代理怎么生成」留在正文提高部分。

### 本讲核心关键词速查

| 关键词 | 一句话大白话 | 例子 |
|-|-|-|
| 泛型 | 让类/方法支持多种类型的「类型参数」 | `List<String>` 只能装字符串 |
| 类型擦除 | 泛型只在编译期检查，运行时是裸类型 | `List<String>` 和 `List<Integer>` 运行时是同一个类 |
| 反射 | 运行时「看穿」一个对象的类、方法、字段 | `obj.getClass().getMethods()` |
| 注解 | 写在类/方法上的标签，本身只是元数据 | `@Override`、`@Service` |
| 动态代理 | 运行时生成「替身对象」拦截方法调用 | Spring 注入给你的其实是代理 |
| CGLIB | 生成**子类**的代理（无接口也能代理） | Spring 对无接口 Bean 用它 |

### 本讲在解决什么问题

- **问题**：Spring 的 `@Autowired` 帮你注入、`@Transactional` 帮你开事务、MyBatis 的 Mapper 接口没写实现类却能调——这些「魔法」到底怎么发生的？
- **答案**：它们几乎都靠**反射读取注解** + **动态代理拦截方法**。这一讲就是把这两块底层机制讲清楚，让框架对你是「可推理的」，而不是「很神奇」。
- **你要带走的一句话**：框架注入给你的 Bean 常常是**代理对象**（替身），方法调用先被代理拦一道做额外处理（注入、事务、日志），再透传给你写的真实逻辑。

### 最简可运行示例（照抄能跑）

```java
import java.lang.reflect.*;

// 注解: 声明一个标签(可作用于方法)
public @interface LogApi {}

// 一个普通类, 方法上打了 @LogApi
public class UserService {
    @LogApi
    public String getUser(Long id) { return "用户" + id; }
}

// 反射: 运行时读取方法上的注解
public class ReflectDemo {
    public static void main(String[] args) throws Exception {
        Method m = UserService.class.getMethod("getUser", Long.class);
        System.out.println(m.isAnnotationPresent(LogApi.class));   // true, 读到了
    }
}
```

> 代码备注（逐行解释）：
> - `public @interface LogApi {}`：定义一个注解，它是「元数据」，本身不做任何事，只负责打标签。
> - `@LogApi` 打在方法上：标记这个方法是「需要记日志的」——Spring 的 `@Transactional` 也这样声明在方法上。
> - `UserService.class.getMethod(...)`：**反射**——运行时拿到类的方法对象，不用 new 实例就能了解它。
> - `m.isAnnotationPresent(LogApi.class)`：运行时判断这个方法有没有打某个注解——Spring 就是靠这个判断「哪些方法要开事务」。

### 关键概念 / 类说明

| 概念 / 类 | 干什么 | 最易踩的坑 |
|-|-|-|
| `<T>` 泛型 | 类型参数，编译期类型安全 | 运行时被擦除，别依赖「运行时是 String」 |
| `Class<?>` | 类的元信息对象 | `getClass()` 拿运行时类，`Xxx.class` 拿编译期类 |
| `@interface` | 定义注解 | 注解可加 `@Retention` 控制生效范围 |
| `Proxy.newProxyInstance` | 生成 JDK 动态代理（要求接口） | 只对接口有效；无接口用 CGLIB |
| `Method.invoke` | 反射调用方法 | 反射掉性能损耗可控，别在热点路径裸用 |

### 常用约定 / 命名提示

- **注解的 Retention**：`SOURCE`（仅源码）/ `CLASS`（编译后字节码）/ `RUNTIME`（运行时，反射能读到）——Spring 的注解都是 `RUNTIME`，因为要运行时反射。
- **动态代理两种**：JDK 动态代理（基于接口） vs CGLIB（生成子类）。Spring Boot 默认倾向 CGLIB（`proxyTargetClass=true`）。
- **看到「框架注入给你的是代理」**：就是这篇讲的动态代理——注入的 Bean 常常不是原始类实例，而是替身。

## 学习内容详情

### 1. 泛型与类型擦除

**类型擦除（Type Erasure）**：Java 泛型只存在于编译期——编译后 `List<String>` 和 `List<Integer>` 是同一个类 `List`，类型参数被「擦」掉了。这与 TS（类型只存在于编译期，但编译产物是 JS 无类型）方向一致，但 Java 的擦除是擦到原始类型（raw type），且运行时无法恢复。

```java
import java.util.List;
import java.util.ArrayList;

List<String> strings = new ArrayList<>();
List<Integer> numbers = new ArrayList<>();

// 运行时它们是同一个 Class —— 泛型参数没进字节码
System.out.println(strings.getClass() == numbers.getClass());   // 输出: true
```

#### 1.1 擦除导致的运行时限制（两个必会例子）

```java
// 限制①: 不能 new T() / 不能 T.class —— 运行时 T 不存在, 没法实例化
public class Box<T> {
    // private T value = new T();          // ❌ 编译错误: T 在运行时是什么都不知道
    private final Class<T> type;           // ✅ 解决方案: 调用方显式把 Class 对象传进来
    public Box(Class<T> type) { this.type = type; }

    public T newInstance() throws Exception {
        return type.getDeclaredConstructor().newInstance();   // 反射创建（见第 2 节）
    }
}

// 限制②: 不能对泛型类型做 instanceof 精确判断
List<String> list = new ArrayList<>();
// if (list instanceof List<String>) {}    // ❌ 编译错误: 运行时没有 List<String> 这个类型
if (list instanceof List) {}               // ✅ 只能判断原始类型
```

> **TS 背景的直觉修正**：TS 的 `interface` / `type` 编译后完全消失，但你可以用类型断言随时「骗」编译器；Java 擦除后连「骗」的对象都没有——想要运行时类型信息，必须显式携带 `Class<T>`（这正是 Spring 大量方法签名带 `Class<T>` 参数的原因）。

### 2. 通配符（Wildcard）与 PECS

**PECS**（Producer Extends, Consumer Super）：如果参数是「生产者」（你从中**读**数据）用 `? extends T`；是「消费者」（你往里**写**数据）用 `? super T`。

```java
import java.util.List;

// ---- 生产者: 我要从 list 里读 Animal ----
// ? extends Animal: 「某种 Animal 的子类列表」, 读出来的一定是 Animal
static double totalWeight(List<? extends Animal> animals) {
    double sum = 0;
    for (Animal a : animals) sum += a.weight();    // ✅ 读: record 的字段用访问器 a.weight(), 不是 a.weight
    // animals.add(new Dog());                   // ❌ 写: 编译器禁止（不知道实际是什么子类的列表）
    return sum;
}

// ---- 消费者: 我要往 list 里写 Dog ----
// ? super Dog: 「某种 Dog 的父类列表」, 装 Dog 进去一定安全
static void addDogs(List<? super Dog> box) {
    box.add(new Dog());                          // ✅ 写: Dog 装进父类列表没问题
    // Dog d = box.get(0);                       // ❌ 读: 读出来的类型只保证是 Object 级别
}

// 注意: record 隐式继承 java.lang.Record, 所以不能 extends 任何类 —— 只能 implements 接口
interface Animal { double weight(); }            // 用接口表达 "有重量的抽象"
record Cat(double weight) implements Animal {}   // record 实现接口合规
record Dog() implements Animal { public double weight() { return 10.0; } }   // 无组件 record 实现接口
```

> 直觉版记忆：`extends` 是「只读货架」——你从货架拿东西（读）安全，但往货架放东西不行；`super` 是「只写回收箱」——你往里扔（写）安全，但从里面拿出来的东西类型不明。

### 3. 反射 API 与性能代价

**反射（Reflection）**：程序在运行时「检查和操作」自身结构的 Ability——拿到任意类的构造器 / 方法 / 字段 / 注解，甚至实例化和调用它。Spring 的组件扫描、MyBatis 的结果映射、JUnit 的测试发现，全是反射驱动的。

```java
import java.lang.reflect.Method;

public class User {
    private String name = "Alice";
    public String greet(String who) { return "Hello, " + who + "! I'm " + name; }
}

public class ReflectDemo {
    public static void main(String[] args) throws Exception {
        // 三种拿到 Class 对象的方式（元信息的入口）
        Class<?> c1 = User.class;                    // ① 类字面量（编译期已知，最推荐）
        Class<?> c2 = new User().getClass();         // ② 对象实例
        Class<?> c3 = Class.forName("User");         // ③ 按名字加载（Spring 扫描就是这么找到类的）

        // 反射调用: 不 new 对象、不看方法名，全靠运行时元信息
        Object user = c1.getDeclaredConstructor().newInstance();   // 无参构造创建实例
        Method greet = c1.getMethod("greet", String.class);        // 找到 greet(String)
        Object result = greet.invoke(user, "Bob");                 // 调用它

        System.out.println(result);    // 输出: Hello, Bob! I'm Alice
    }
}
```

**性能代价与框架的应对**：反射调用比直接调用慢（要走方法查找 + 安全检查 + 装箱），且 JIT 难以内联优化。框架的做法：① 缓存 `Method` / `Constructor` 对象（查找只做一次）；② 高频路径改用字节码生成（如 `LambdaMetafactory`、CGLIB）替代裸反射。所以「框架里的反射 ≠ 裸反射」——别拿裸反射的 benchmark 数据否定整个 Spring；反射的开销真正成为问题的，主要出现在「裸用且高频」的自研代码里。

### 4. 注解的 Retention 策略

**注解（Annotation）**：贴在类 / 方法 / 字段上的「标签」——本身只是元数据，没有任何行为；行为来自**处理它的代码**（编译器、字节码工具、运行时框架）。类比：注解是 TS 的装饰器实验版思路，但 Java 注解默认更「被动」——纯数据。

**为什么需要三种 Retention**：注解的消费者分布在生命周期的不同节点——编译器（SOURCE）、字节码工具（CLASS）、运行时框架（RUNTIME）；`@Retention` 就是声明「这份元数据为谁而留、留到哪一步」——留错档位要么反射读不到（CLASS），要么白白占用内存（不需要运行时却标了 RUNTIME）。

```java
import java.lang.annotation.*;

public class RetentionDemo {
    // SOURCE: 只活在源码里, 编译后丢弃 —— 给编译器/lint 看的
    // 代表: @Override / Lombok 的 @Data（编译期生成代码后就没用了）
    @Retention(RetentionPolicy.SOURCE)
    @interface MyLint {}

    // CLASS: 编译进 class 文件, 但运行时反射读不到 —— 给字节码工具看的（很少手写）
    @Retention(RetentionPolicy.CLASS)
    @interface MyBytecodeTool {}

    // RUNTIME: 运行时可反射读取 —— Spring/MyBatis/Bean Validation 的全部注解都是这档
    @Retention(RetentionPolicy.RUNTIME)
    @interface MyRuntime {
        String value() default "";    // 注解可以带参数（属性）, default 给默认值
    }

    @MyRuntime("user-service")
    static class UserService {}

    public static void main(String[] args) {
        // Spring @Component 扫描的本质就是这一行: 反射读注解 → 拿到元数据 → 决定怎么装配
        MyRuntime anno = UserService.class.getAnnotation(MyRuntime.class);
        System.out.println(anno.value());   // 输出: user-service
    }
}
```

| 策略 | 生命周期 | 典型消费者 |
|-|-|-|
| `SOURCE` | 只到编译期 | `@Override` / Lombok `@Data` |
| `CLASS` | 进 class 文件，运行时不可见 | 字节码工具（很少手写） |
| `RUNTIME` | 运行时可反射读取 | Spring / MyBatis / Bean Validation 的几乎全部注解 |

### 5. JDK 动态代理 vs CGLIB

**动态代理（Dynamic Proxy）**：运行时凭空生成一个「代理对象」，拦截对目标对象的方法调用，插入你的增强逻辑。这是 AOP（`@Transactional` / `@Around`）和 MyBatis Mapper 的实现底座。

**为什么 JDK 代理必须基于接口**：`Proxy.newProxyInstance` 是在运行时**新建一个类**（如 `$Proxy0`）去实现你传入的接口——Java 单继承，这个新类只能继承 `java.lang.reflect.Proxy`，无法再「伪装」成一个具体类；想代理无接口的类，只能走 CGLIB 的「生成子类」路线。

```java
import java.lang.reflect.*;

// ---- 第 1 步: 定义接口 + 真实实现 ----
interface OrderService {
    String create(String sku);
}
class OrderServiceImpl implements OrderService {
    public String create(String sku) { return "订单已创建: " + sku; }
}

// ---- 第 2 步: InvocationHandler = 「拦截逻辑」 ----
class LoggingHandler implements InvocationHandler {
    private final Object target;                  // 被代理的真实对象
    LoggingHandler(Object target) { this.target = target; }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        System.out.println("[前置] 调用 " + method.getName() + " 参数 " + args[0]);
        Object result = method.invoke(target, args);   // 放行: 反射调用真实对象
        System.out.println("[后置] 返回 " + result);
        return result;
    }
}

// ---- 第 3 步: 运行时生成代理类（编译期根本不存在 OrderService$Proxy0 这个类） ----
public class ProxyDemo {
    public static void main(String[] args) {
        OrderService real = new OrderServiceImpl();
        OrderService proxy = (OrderService) Proxy.newProxyInstance(
            real.getClass().getClassLoader(),            // 用哪个类加载器
            new Class<?>[]{ OrderService.class },        // 代理要实现哪些接口
            new LoggingHandler(real));                   // 拦截逻辑

        proxy.create("SKU-001");
        // 输出:
        // [前置] 调用 create 参数 SKU-001
        // [后置] 返回 订单已创建: SKU-001
    }
}
```

**MyBatis Mapper 之谜的答案**：你只定义了 `interface OrderMapper`，没有任何实现类，`sqlSession.getMapper(OrderMapper.class)` 却能返回能跑 SQL 的对象——它就是 `Proxy.newProxyInstance` 生成的代理，`InvocationHandler.invoke` 里根据「方法名 + 注解/XML 元数据」拼出 SQL 并执行。现在你知道这个魔术的全过程了。

#### 5.1 JDK 代理 vs CGLIB 对比

| 维度 | JDK 动态代理 | CGLIB |
|-|-|-|
| 原理 | 运行时**实现接口**（`Proxy` + `InvocationHandler`） | 运行时**生成目标类的子类**（字节码增强，`MethodInterceptor`） |
| 要求 | 目标必须有接口 | 类与方法不能是 final（子类覆盖不了） |
| Spring 默认 | 需显式配置（Boot 下不默认走它） | **Spring Boot 默认**（`proxyTargetClass=true`，CGLIB 优先，无论有无接口） |

- **Spring Boot 的默认是 CGLIB**：`proxyTargetClass=true`，无论有无接口都 CGLIB 优先，JDK 代理需显式配置——直接效果是注入时用具体类型（而不是接口）也能注入。JDK 代理的优点（不生成子类、无 final 限制、类型安全由接口契约保证）依旧成立，只是「默认」不再是它。
- CGLIB 的拦截接口是 `MethodInterceptor.intercept(obj, method, args, methodProxy)`——能力同 `InvocationHandler`，但基于继承而非接口。
- **手写 CGLIB 的第一大坑**：`MethodInterceptor` 里调目标逻辑用 `methodProxy.invokeSuper(obj, args)`；误用 `method.invoke(obj)` 会再次进入代理自身 → 无限递归爆栈。

> ⏸️ **短期可以不学**：手写 CGLIB 的 `MethodInterceptor` / `invokeSuper` 细节——生产上你几乎只会「用」Spring 配好的代理（`@Transactional` / `@Aspect`），不会手写字节码增强。**何时回来学**：要自研 AOP / 代理框架、或面试被深挖「CGLIB 底层拦截机制」时。**面试最低要求**：能说清「CGLIB 基于生成子类、final 方法不可代理、Spring Boot 默认用它」即可。

### 坑点提醒

- **别拿 `List<Object>` 接 `List<String>`**：泛型不协变（`List<String>` 不是 `List<Object>` 的子类）——协变的方向问题正是通配符存在的理由，TS 里数组默认协变埋的坑（`Array<Cat>` 赋给 `Array<Animal>` 后可写入 Dog）在 Java 编译期就被拦下。
- **反射绕过泛型检查**：`List.class.getMethod("add", Object.class)` 能往 `List<Integer>` 里塞字符串——擦除的世界里运行时没人拦你，出来混迟早 ClassCastException。
- **`getDeclaredMethods` 与 `getMethods`**：前者含私有方法不含继承，后者含 public 继承链——框架代码里混用是扫描不全的经典 bug。
- **CGLIB 代理 final 方法静默失效**：final 方法无法被子类覆盖，调用时直接落到目标对象、增强逻辑不执行——`@Transactional` 放在 final 方法上不生效的根源之一。
- **`Class.forName` 抛 checked 异常**：类不存在 / 不在 classpath 时 `ClassNotFoundException`——动态加载要处理它，别裸抛。

## 常见面试题

### Q1：Java 泛型的类型擦除是什么？运行时有哪些限制？怎么获取泛型的实际类型？
**答**：类型擦除（Type Erasure）指 Java 泛型只在编译期做类型检查，编译后类型参数被擦除为原始类型（raw type）——`List<String>` 与 `List<Integer>` 运行时是同一个 `List` 类，字节码里没有泛型参数信息。由此产生三个典型运行时限制：① 不能 `new T()`、不能取 `T.class`（运行时 T 不存在）；② 不能对泛型类型做精确 instanceof；③ 泛型数组创建受限（`new T[]` 非法）。解决办法是显式携带类型信息：构造器接收 `Class<T>` 参数，或用匿名子类惯用法——`new TypeToken<List<String>>(){}` 利用「子类继承的泛型签名写入字节码」，在运行时通过 `getGenericSuperclass()` + `ParameterizedType` 还原实际类型参数（Gson 的 TypeToken、MyBatis 的 TypeHandler 都靠这个）。工程启示：泛型是编译期契约，运行时需要类型信息必须显式传递，这也是 Spring 大量 API 签名带 `Class<T>` 的原因。

### Q2：JDK 动态代理和 CGLIB 的区别？Spring 为什么默认使用 CGLIB？
**答**：两者都是运行时生成代理类，机制不同：JDK 动态代理用 `Proxy.newProxyInstance` 生成一个**实现目标接口**的类（`$Proxy0`），拦截逻辑在 `InvocationHandler.invoke` 里；CGLIB 用字节码技术**生成目标类的子类**，拦截逻辑在 `MethodInterceptor.intercept`。差异：① 要求不同——JDK 代理必须基于接口；CGLIB 要求类和方法非 final（final 无法被子类覆盖，代理会静默失效）。② 性能——JDK 8 之后两者差距很小，CGLIB 需额外生成子类字节码。③ Spring Boot 默认 CGLIB（`proxyTargetClass=true`），无论有无接口都优先子类代理，直接效果是**按具体类型注入也能命中代理**（JDK 代理下只能按接口注入）。工程关键认知：注入的是代理——同类内部 `this` 调用不经过代理，`@Transactional` 自调用失效就是这个原因。

### Q3：反射的性能开销来自哪里？框架是怎么规避的？
**答**：反射开销主要来自四方面：① 运行时按名字查找方法 / 字段，无法像直接调用那样编译期确定调用点；② 参数装箱与类型转换检查；③ 安全校验（访问权限检查）；④ JIT 优化受限——调用点不固定，方法内联等优化无法生效，动态调用还会打断既有的内联链。框架的应对三板斧：① 缓存 `Method` / `Constructor` 对象，查找只做一次；② 高频路径改用字节码生成——CGLIB、`LambdaMetafactory`（方法句柄）替代裸反射，性能接近直接调用；③ 用 `MethodHandle` / `VarHandle` 这类 JIT 可优化的底层 API。所以「框架里的反射 ≠ 裸反射」——Spring 的性能瓶颈不在反射本身；裸反射真正成为问题的是自研代码里高频调用，此时应缓存 Method 或换代码生成方案。

### Q4：为什么 `@Transactional` 加在 private 或 final 方法上不生效？
**答**：`@Transactional` 生效依赖 AOP 代理：Spring 创建 Bean 时发现需要事务增强，会生成代理对象并注入；调用方通过代理调方法，代理先开启事务再透传。private 方法不生效的原因：JDK 代理只能拦接口方法，CGLIB 是子类代理——子类无法覆盖 private 方法，代理根本「插不进」这个调用点，事务逻辑自然不执行。final 方法同理：CGLIB 靠覆写实现增强，final 方法不可覆写，调用直接落到目标对象。还有一个高频陷阱是**同类自调用**：`this.methodB()` 内部调用不走代理（`this` 是原始对象不是代理），所以同类里 `methodA` 调 `@Transactional` 的 `methodB`，事务不生效——解法是把事务方法放到另一个 Bean，或用 `AopContext.currentProxy()` 取代理再调。这道题的本质：代理只拦「从代理入口进入的调用」。
