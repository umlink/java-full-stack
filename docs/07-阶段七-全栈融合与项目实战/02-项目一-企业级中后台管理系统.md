### 3. 核心功能实现

#### 3.1 RBAC（表结构 + 鉴权链路）

**RBAC（Role-Based Access Control，基于角色的访问控制）**：权限不直接挂用户，而是先挂角色、再把角色挂用户——中间多一层「角色」，授权管理才不爆炸。为什么必须抽这一层：用户与权限都是多对多，直接挂钩意味着新增一个权限要改所有用户、来一个新员工要配几十个权限；抽角色后，权限变化只动角色，人员流动只动用户-角色映射，两边互不牵连。落地为五表（用户-角色-权限 + 两张关联表）：

```sql
-- RBAC 五表(用户-角色-权限三级 + 两张关联): 菜单/按钮/接口三类权限共用 perm 表
CREATE TABLE sys_user (id BIGINT PRIMARY KEY, username VARCHAR(64) UNIQUE, password VARCHAR(100), ...);
CREATE TABLE sys_role (id BIGINT PRIMARY KEY, code VARCHAR(64) UNIQUE, name VARCHAR(64), ...);  -- admin/ops/viewer
CREATE TABLE sys_perm (id BIGINT PRIMARY KEY, code VARCHAR(128) UNIQUE,   -- 权限编码: system:user:add
                       type TINYINT, menu_id BIGINT, ...);                  -- 1 菜单 2 按钮 3 接口
CREATE TABLE sys_user_role (user_id BIGINT, role_id BIGINT, PRIMARY KEY(user_id, role_id));
CREATE TABLE sys_role_perm (role_id BIGINT, perm_id BIGINT, PRIMARY KEY(role_id, perm_id));
-- 鉴权链路: 登录 → 查 role → 查 perm codes → 塞进 JWT claims/SecurityContext
--          → @PreAuthorize("hasAuthority('system:user:add')") 逐接口判(code 即权限)
```

三类权限各管一层：**菜单权限** → 前端路由守卫按角色动态下发；**按钮权限** → 前端指令/组件封装控制显隐；**接口权限** → 后端 `@PreAuthorize` 判 code。别把三类都塞回后端——前端隐藏只是体验，接口权限才是底线（越权测试一跑一个准）。

#### 3.2 字典管理（Redis 缓存的落地）

```java
// 字典是"读极多写极少"的教科书签场: 启动全量预热 + 变更时主动失效
@Service
public class DictService {
    private final StringRedisTemplate redis;
    private static final String KEY = "dict:type:";    // dict:type:order_status → JSON

    public List<DictItem> byType(String type) {
        var cached = redis.opsForValue().get(KEY + type);
        if (cached != null) return parse(cached);                       // 命中: 不碰 DB
        var items = dictRepo.byType(type);
        redis.opsForValue().set(KEY + type, json(items),                  // 回填: 24h + 随机扰动(防雪崩,阶段三第4讲)
                Duration.ofHours(24).plusMinutes(random(30)));
        return items;
    }

    @Transactional
    public void update(DictItem item) {
        dictRepo.update(item);
        redis.delete(KEY + item.type());                                 // 先更 DB 再删缓存(Cache-Aside 标准)
        // 单机管理后台可不做延迟双删; 上集群/主从后按阶段三第 2 讲的窗口评估
    }
}
```

#### 3.3 操作日志审计（AOP + 异步）

```java
// 注解声明"记什么", 切面统一"怎么记" —— 业务代码零侵入
@Target(METHOD) @Retention(RUNTIME)
public @interface OpLog { String value(); }              // @OpLog("删除用户")

@Aspect @Component
public class OpLogAspect {
    private final ApplicationEventPublisher events;      // 日志发布出去, 切面只做采集

    @Around("@annotation(opLog)")
    public Object around(ProceedingJoinPoint pjp, OpLog opLog) throws Throwable {
        var entry = new OperLog(opLog.value(), SecurityUtils.username(),        // 谁
                pjp.getSignature().toShortString(), safeArgs(pjp.getArgs()),     // 干了什么(参数脱敏!)
                LocalDateTime.now());
        long t0 = System.nanoTime();
        try { var r = pjp.proceed(); entry.success(t0); return r; }
        catch (Throwable e) { entry.fail(e); throw e; }
        finally { events.publishEvent(entry); }         // 发布不阻塞主链路
    }

    @Async @EventListener @Transactional(propagation = Propagation.REQUIRES_NEW)   // 独立新事务: 主事务回滚也要留下这行审计
    public void onLog(OperLog e) { operLogRepo.insert(e); }
}
```

## 常见面试题

### Q1：RBAC 权限模型怎么设计？菜单、按钮、接口三层权限分别在哪一层校验？

**答**：RBAC（Role-Based Access Control）的核心是「权限不挂用户、挂角色」——用户→角色→权限三级，落地为五张表（用户/角色/权限 + 用户-角色、角色-权限两张关联表）。为什么抽角色这一层：用户和权限都是多对多，直接挂钩会让授权管理爆炸（来一个新员工要配几十个权限），抽层后权限变更只动角色、人员变动只动用户-角色映射，互不牵连。三类权限各管一层：菜单权限在前端路由守卫（按角色动态下发路由），按钮权限在前端（指令/组件封装控制显隐），接口权限在后端（@PreAuthorize 判权限码）——记住「前端隐藏只是体验、后端校验才是底线」，越权测试一跑一个准。扩展方向：多租户时权限表要加租户维度；更要主动说出边界——RBAC 只解决「能不能访问接口」，管不了「能访问哪些数据行」，那是数据权限（行级）的事。

### Q2：接口权限只能管「能不能访问」，数据权限（行级权限）怎么实现？

**答**：数据权限解决「同一个接口，不同角色看到不同数据行」——比如部门主管看全部门、普通员工只看自己。实现分三步：一是权限模型上给用户或角色挂「数据范围」属性（全部 / 本部门及以下 / 本部门 / 本人）；二是登录后把用户 id、部门 id、数据范围解析结果放进 SecurityContext / ThreadLocal；三是在 SQL 层拼过滤条件——MyBatis-Plus 可用拦截器（Interceptor）统一在查询上追加 data_scope 条件，业务代码无侵入。两个关键坑：一是数据权限过滤必须在 SQL 里做（数据库层限行），不能查全量再在内存/前端过滤——数据已经出库才想起来挡就是泄露；二是数据范围条件必须参数化防注入，且部门树要支持「含下级」（递归取子部门）。面试说清「属性建模 + 上下文传递 + SQL 拦截」三步链路即可，能主动点出「防注入、含下级」两个细节就是加分。

### Q3：操作日志/审计系统怎么实现？记什么、怎么记、怎么不拖垮主链路？

**答**：三件事：记什么、怎么记、性能与安全。记什么：谁（用户）、何时、哪个接口、什么操作（@OpLog("删除用户")）、参数（脱敏后的）、结果（成功/失败、耗时）。怎么记：用 AOP 切面统一采集——业务代码只加注解，切面 @Around 包住目标方法，把操作事件发布到 Spring 事件，监听器异步落库；关键细节是监听器用 REQUIRES_NEW 开独立新事务——主事务回滚也要留下这行审计，审计不能跟着业务一起消失。性能与安全：参数脱敏不是可选步骤——审计表存了明文密码就是新的泄露源；写入走异步 + 独立表，量大后按月分表。为什么用 AOP：审计是横切关注点，散在每个方法里手动记必然漏记且难维护，切面把「采集」集中，业务只声明「记什么」。面试说出「脱敏 + 独立事务 + 异步」三个细节就是过关。

### Q4：字典这种「读极多写极少」的数据，缓存方案怎么设计？先更 DB 还是先删缓存？

**答**：字典是 Cache-Aside 的教科书场景：启动全量预热进缓存，读取先查缓存、miss 回填，变更时「先更 DB、再删缓存」。为什么先更 DB 再删缓存：主动更新缓存会让两个数据源耦合（写 DB 和写缓存是两个动作，怎么都做不到同一时刻），而删缓存后下次读自然回填新值，代价只是一次 DB 读；更重要的是先删缓存再更 DB 的窗口里，并发读会把旧值回填，所以顺序必须是「先 DB 后删缓存」。主从复制有延迟的极端情况要「延迟双删」（删 → 等主从同步 → 再删一次），单机管理后台通常不用。另一个高频追问：字典量小、变更极低频，为什么不直接用本地 Caffeine 缓存？——本地缓存每实例一份，多实例下变更要广播失效（Redis Pub/Sub 或多级缓存刷新），复杂度高于收益；而且字典数据天然适合集中存储统一维护，Redis 单级在管理后台场景够用。
