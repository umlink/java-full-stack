### 核心链路速览（正文展开更细）

```text
RAG 知识库:  文档解析 → 切分 → 向量化 → 存向量库(离线索引)
            用户提问 → 问题向量化 → 检索(top-k) → 拼Prompt → LLM生成 → 回答
AI 工程化:   重试(指数退避) + 降级(大→小→检索摘要) + 成本(打点+汇总)
```

> 说明（逐行解释）：
> - **RAG（Retrieval-Augmented Generation，检索增强生成）**：把文档切分、向量化、存进向量库；用户提问时先检索相关知识再让模型回答——防止「模型不知道还在编」。
> - **向量库选型**：默认用 **PGVector**（复用已有 PostgreSQL，零额外部署）；量大再到百万级才考虑 Milvus——别一开始就上重组件。
> - **流式对话**：用 SSE 逐 token 推送，前端打字机效果；断线重连、取消生成要处理。
> - **AI 工程化**：把 LLM 当脆弱外部依赖——重试（指数退避）、降级（大模型→小模型→纯检索摘要）、成本（token 打点 + 汇总）。

### 2. RAG 知识库全链路

```text
文档解析 → 切分(chunking) → 向量化(embedding 嵌入: 文本→高维语义向量, 语义相近则向量距离近, 「相似检索」就靠这个) → 存向量库  ← 离线索引链路
用户提问 → 问题向量化 → 相似检索(top-k) → 拼 Prompt(带引用上下文) → LLM 生成 → 回答   ← 在线问答链路
```

```java
@Service
public class RagService {
    private final VectorStore vectorStore;        // Spring AI 抽象, Milvus/PGVector 换实现不换代码
    private final ChatClient chat;

    // ① 离线索引: 切分质量 > 模型大小 —— chunk 400~800 token + 10~15% overlap 起步
    public void ingest(List<Document> docs) {
        // 注: TokenTextSplitter 的具体参数语义以 Spring AI 当前版本文档为准(不同版本构造器参数含义略有差异)
        var chunks = new TokenTextSplitter(600, 80).apply(docs);   // 这里的 600/80 按官方参数字典解释, 此处示意
        vectorStore.add(chunks);                                   // 内部批量向量化, 注意批大小与超时
    }

    // ② 在线检索增强: 先查上下文再问模型
    public String answer(String question) {
        List<Document> ctx = vectorStore.similaritySearch(
            SearchRequest.query(question).withTopK(5)
                .withSimilarityThreshold(0.75));                   // 阈值挡"看着像其实无关"
        return chat.prompt()
            .system(s -> s.text("""
                仅依据以下资料回答, 没有依据时直说"资料中未找到"; 引用处标 [文档标题]。
                资料: {ctx}""").param("ctx", render(ctx)))
            .user(question)
            .call().content();
    }
}
```

- **Rerank 调优位（进阶扩展）**：top-5 粗召 → rerank 模型精排取 top-3——**检索质量不够时才加的优化，不是起点**。先优化召回与切分，最后才换大模型（性价比直觉同阶段六「自上而下优化」）；主链路只保「文档解析 → 向量检索 → LLM 生成」。

> ⏸️ **短期可以不学**：Rerank 精排属于检索调优的进阶项——主线先把「切分 → 召回 → LLM 生成」主链路跑通即可，别在检索精度上恋战。**何时回来学**：知识库问答准确率不够、Bad-case 集中在「召回错」时。**面试最低要求**：说出 Rerank 解决什么问题（粗召回 + 精排两层结构）与「先优化召回与切分，最后才换大模型」的调优次序。
- 空召回也要生成回答还是拒答？产品决策：**检索置信低时拒答 + 引导人工**——「不许模型补齐不存在的数据」是跨语言的铁律。相似度阈值 0.75 不是拍脑袋定的——用小评测集扫 0.6-0.9 区间，选「召回全 + 噪音少」的平衡点。

### 3. 流式对话（SSE，Server-Sent Events）

```java
// WebFlux 的合理主场(阶段二第 4 讲判断): token 逐段推送, 前端打字机
@GetMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> chatStream(@RequestParam String q) {
    return chat.prompt().user(q).stream().content()     // Spring AI stream(): Flux token 流
        .timeout(Duration.ofSeconds(60))                // 60s 没新 token = 假死, 断开给前端
        .onErrorResume(e -> Flux.just("[系统繁忙, 请重试]"));   // 半句也要优雅收尾
}
// 前端: EventSource / fetch 流读取逐段渲染; 断线重连带 last-token 标记防重复
```

- 流式链路的可观测：**每个对话一个 trace_id**（阶段二 MDC + 阶段五 Tracing），LLM 调用的 TTFT（Time To First Token，首 token 时间）与总耗时单独打点——「慢不慢」对 AI 应用是核心体验指标。
- 边界处理三件套：客户端断连（`doOnCancel` 里 stop 模型生成省钱）、半句超时（上面的 timeout）、内容审核命中（推「敏感词」帧而非 error）。

### 5. AI 工程化：把 LLM 当「脆弱的外部依赖」治理

```java
// 重试/降级/成本三件事, 全是后端传统手艺的新场景:
@Service
public class LlmClient {
    @Retryable(retryFor = TimeoutException.class, maxAttempts = 2,        // 只重试幂等/只读
               backoff = @Backoff(delay = 2000, multiplier = 2))         // 指数退避(Exponential Backoff), LLM 429(限流)常见
    @CircuitBreaker(name = "llm", fallbackMethod = "degrade")
    public ChatResponse call(ChatRequest req) { return rawCall(req); }

    ChatResponse degrade(ChatRequest req, Throwable t) {
        return chatSmallModel(req);                                       // 降级链: 大模型→小模型→纯检索摘要→拒答兜底
    }
}
```

- **成本控制**：token 用量每次调用打点（usage 元数据）+ 每日汇总即可起步；**「按用户/场景配额限流」先不做**——那要额外做一套计量系统（Redis 计数 + 定时清理 + 用户账单），超出本可选项的必要复杂度。有需要再按阶段六限流器叠加。

> ⏸️ **短期可以不学**：按用户/场景的配额限流（计量系统）是 AI 功能到了「成本失控」阶段才需要的治理——起步阶段打点 + 日汇总足够。**何时回来学**：AI 成本曲线明显上升、需要按用户治理时。**面试最低要求**：一句话——「先打点看清钱花哪了，再上配额治理」。
- **与中间件的组合清单**：对话历史（Redis TTL + PG 归档）、检索结果缓存（embedding 缓存省向量检索费）、敏感词前置（挡在调模型之前）、审计日志（谁问了什么、模型答了什么）、**Prompt 注入检测**（用户输入里的「忽略以上指令」要当攻击面看，阶段六第 5 讲的新变种）。

### 坑点提醒

- **temperature 当"随机种子"用**：0 不等于可复现（模型侧仍非确定）——评测与回归要跑多次取分布，别拿单次结果换 Prompt。
- **RAG 把整篇文档塞进上下文**：token 成本与「中间遗忘」双输——切分 + 召回 + 精排的目的就是控制上下文规模。
- **流式接口没算超时预算**：网关 60s / 模型 120s 的生成会静默截断——逐 token 的 idle timeout 比总超时更适合流式（上面 60s 的写法）。
- **向量库当数据库用**：metadata 过滤能力弱、更新有延迟——业务真相进 MySQL / PG，向量库是检索加速层（ES 同款定位）。

## 常见面试题

### Q1：RAG（Retrieval-Augmented Generation）的完整链路是什么？检索质量怎么调优？

**答**：RAG 解决的核心问题是「模型不知道的还在编」——先检索相关知识再让模型回答，回答有依据。全链路分离线与在线两段：离线索引——文档解析 → 切分（chunking）→ 向量化（embedding）→ 存向量库；在线问答——问题向量化 → 相似度检索（top-k + 阈值）→ 拼 Prompt（带引用上下文）→ LLM 生成。调优次序：先优化召回与切分，最后才换大模型——切分质量大于模型大小，chunk 400~800 token + 10~15% overlap 起步，太小丢上下文、太大稀释语义；检索的坑是「看着像其实无关」，用相似度阈值（小评测集扫 0.6-0.9 找平衡点）挡掉，检索置信低时拒答 + 引导人工，「不许模型补齐不存在的数据」是铁律。进阶是 Rerank：top-5 粗召 → 精排取 top-3，检索精度不够才加。工程上注意：向量库是检索加速层，业务真相在 MySQL/PG；embedding 结果可缓存省向量检索费。

### Q2：AI 对话的流式输出为什么用 SSE 而不是 WebSocket？断线、超时怎么处理？

**答**：SSE（Server-Sent Events）是 HTTP 上的单向服务端推送。选它而不是 WebSocket 的理由：一是单向足够——AI 对话是「客户端问一句、服务端流式推 token」，不需要上行通道，WebSocket 的双向能力用不上；二是走标准 HTTP——天然过网关/代理、自动带 Cookie 鉴权、浏览器 EventSource 自带自动重连，WebSocket 要自己实现心跳与重连；三是协议简单，TEXT_EVENT_STREAM 就是 HTTP response 分块。实现：Spring WebFlux 返回 Flux<String> 逐 token 推送（token 按生成量计费，流式让首 token 尽快可见，用户体验与成本双赢）。三个边界必须处理：客户端断连——doOnCancel 里 stop 模型生成，省钱；半句超时——流式不能用总超时，要用「逐 token 的 idle timeout」（60s 没新 token 判假死），网关/模型总超时可能静默截断；内容审核命中——推「敏感词」帧而不是 error。可观测：每对话一个 trace_id，TTFT（Time To First Token，首 token 时间）单独打点——AI 应用「慢不慢」的核心指标。

### Q3：长对话怎么管理上下文？token 窗口满了怎么办？

**答**：先讲约束：LLM 上下文窗口有限且按 token 计费，多轮对话把历史全塞回去，成本线性涨、质量还下降（模型对超长上下文「中间遗忘」）。方案按「信息密度」分层：一是短对话直接拼最近 N 轮；二是滑动窗口——只保留最近 N 轮完整消息，更早的丢弃；三是摘要压缩——定期用 LLM 把旧历史总结成一段摘要，对话继续时带「摘要 + 最近 N 轮」，叫「摘要 + 窗口」混合策略；四是结构化压缩——只保留对后续回答有影响的实体与结论。工程上对话历史存 Redis（TTL）+ PG 归档，每次请求按策略组装 messages 数组。两个关键点：一是「上下文裁剪」要和 RAG 配合——RAG 场景里上下文塞的是检索结果而非全量历史；二是压缩本身有成本（摘要也是 token），按对话轮数分级取舍。面试说清「滑动窗口 → 摘要压缩 → 结构化」的递进即可。

### Q4：Function Calling / 工具调用怎么设计？模型返回的调用参数怎么保证安全？

**答**：Function Calling 是让 LLM 输出「该调哪个函数 + 参数 JSON」而不是直接回答——模型只决策，应用层执行并回填结果。链路：注册函数描述（名称、参数 JSON Schema、用途说明）→ 模型判断需要时返回 function_call → 应用校验参数（JSON Schema 校验 + 函数白名单）→ 执行真实函数 → 结果作为新消息回填 → 模型基于结果给出最终回答。三个工程要点：一是参数校验绝不能省——模型的输出是「文本生成」不是类型系统，可能漏参、类型错、甚至注入恶意内容，Schema 校验 + 枚举白名单是底线；二是工具调用要幂等与超时——模型可能重复调用同一工具（比如查两次库存），写操作要防重；三是循环控制——模型和工具之间可能来回多轮，要设最大迭代次数防死循环烧钱。降级：工具挂了不能把错误原样丢给模型，回「工具暂不可用」让模型换话术。说清「模型只决策、应用执行、校验与兜底在应用侧」这个分工就是过关。

### Q5：把 LLM 当外部依赖，稳定性与成本怎么治理？

**答**：核心心态是把 LLM 当「脆弱的外部依赖」——它会超时、429 限流、内容审核、服务商变更，治理手段全是后端传统手艺的新场景。稳定性三件套：重试（只重试幂等/只读请求，指数退避 Exponential Backoff，LLM 429 是常态）；降级链（大模型 → 小模型 → 纯检索摘要 → 拒答兜底，熔断器 CircuitBreaker）；可观测（每次调用打点：耗时、TTFT、usage token、错误码，trace_id 贯穿）。成本治理从「先打点、后治理」开始：每次调用把 usage 元数据（input/output token、模型、场景）落库，每日汇总看成本分布，先搞清楚钱花哪了；按用户/场景的配额限流属于进阶，要额外做一套计量系统（Redis 计数 + 定时清理 + 用户账单）。缓存是省钱大头：embedding 结果缓存（同语义问题只检索一次）、RAG 检索结果缓存、常见问题整段回答缓存。安全侧：Prompt 注入检测——「忽略以上指令」要当攻击面看；敏感词前置挡在调模型之前；审计日志记谁问了什么、模型答了什么。把「重试 / 降级 / 打点 / 缓存 / 审计」五件事说全就够。
