## 快速入门

> 本节为「容量压测速览」：先认识容量怎么估算、压测是干嘛的；「Little's Law、全链路压测」留在正文提高部分。

### 本讲核心关键词速查

| 关键词 | 一句话大白话 | 例子 |
|-|-|-|
| QPS | 每秒请求数 | 系统负载 |
| RT（响应时间） | 单次请求耗时 | 50ms |
| Little's Law | 并发 = QPS × RT | 算出需要多少并发 |
| 峰值系数 | 高峰是平时的几倍 | 大促 5 倍 |
| 压测 | 模拟高并发测系统水位 | k6 模拟 5w 并发 |
| 容量水位 | 系统能扛到哪 | 拐点 QPS |
| 扩容预案 | 到什么水位扩什么 | 加实例/加分片 |
| 降级预案 | 极限流量砍什么 | 保下单砍推荐 |

### 本讲在解决什么问题

- **问题**：大促前系统能扛多少？不是猜，而是**算**——从业务目标（日单量）推导 QPS → 并发 → 机器数。压测验证算得对不对，产出「水位 + 扩容 + 降级」三件套。
- **你要带走的一句话**：容量 = **Little's Law（并发 = QPS × RT）**推出来的；压测是验证；**三件套**（水位报告/扩容预案/降级预案）才是最终交付物，不是一份报告就完事。

### 最简推演（正文展开更细）

```text
日订单 500w → 峰值(20:00-22:00 占全天 30%) → 峰值 QPS ≈ 500w × 0.3 / 7200s ≈ 208
→ 单请求 RT 假设 100ms → 并发 ≈ 208 × 0.1 = 21
→ 单台能扛 100 QPS → 需 ≈ 3 台
```

> 说明（逐行解释）：
> - 从业务目标出发：日单 500w，算出**峰值 QPS**（高峰时段集中全天 30% 订单）。
> - 用 **Little's Law**：并发 = QPS × RT（208 × 0.1s ≈ 21 个并发）。
> - 再除单台机器能扛的量（假设 100 QPS），得出需要几台。
> - 这就是「从业务目标到机器数量」的算术链——容量是算出来的，不是拍脑袋。

### 关键概念说明

| 概念 | 干什么 | 最易踩的坑 |
|-|-|-|
| QPS | 每秒请求 | 峰值用高峰期，别用平均 |
| Little's Law | 并发=QPS×RT | RT 用真实值，别猜 |
| 压测 | 模拟高并发 | 只压单接口危险，要做场景压测 |
| 影子表 | 压测数据隔离 | 影子表 DDL 要和主表同步，定期清理 |
| 扩容预案 | 到水位扩什么 | 和 HPA 阈值对齐 |
| 降级预案 | 极限流量砍什么 | 每个系统有自己的「保下单」 |

### 常用约定 / 命名提示

- **压测工具**：k6（前端友好）、Gatling、JMeter——前端出身首选 k6（JS 写脚本）。
- **三件套才是交付**：水位报告（能扛到哪）+ 扩容预案（到水位扩什么）+ 降级预案（极限砍什么）——不是一份报告就完。
- **压测数据要隔离**：全链路压测用影子表 + 挡板，别污染生产数据；影子表要定期清理。

## 学习内容详情

### 1. 容量评估的算术链

**Little's Law**：`并发数 = QPS × RT（秒）`——系统内「在途请求」的恒定关系。

```text
从业务目标反推机器数的完整链路:

  日订单 500w, 20:00-22:00 两小时内集中全天 30% 的订单
  → 峰值 QPS = 500w×0.3 / 7200s ≈ 208
  × 峰值系数 3(热点活动突发) × 业务冗余 1.3(增长/突发余量) = 容量目标 ≈ 810 QPS

  压测基线: 单实例(order-service, 4C8G) p99 达标下最大 120 QPS
  → 按容量目标需实例数 = ⌈810/120⌉ ≈ 7 台
  → 再 × 1.3(运维高可用余量: 滚动发布 + 单机故障兜底) ≈ 9 → 10 个 Pod

  (注意: 上面两个 1.3 不是重复计——前者是"业务增长余量", 后者是"运维高可用余量", 口径不同)

  下游资源跟着算(并发数 = QPS × RT):
  → DB: 810 × 0.03s ≈ 24 连接稳态并发 → 连接池总配额 ≥50 + 余量; 单实例池 = 50/10 = 5
  → Redis: 读放大 810×3(每请求3次缓存) ≈ 2.4k QPS —— 单分片够, 热 key 才要担心
  → MQ: 峰值写入 + 重放预算(积压 2 小时要 3 倍消费能力追回)
```

- 两个易错点：**平均值陷阱**（RT 用 p99 代入 Little's Law 会高估并发，用 p50 会低估尾延迟风险——容量场景一般 p90/p99 双算取保守）；**下游放大**（重试 ×2、缓存击穿瞬时全打 DB——容量是全链路的，不只是应用层）。

### 2. 单接口 vs 场景压测

| 维度 | 单接口压测 | 场景压测 |
|-|-|-|
| 流量 | 打一个接口猛压 | 按真实混合比例（80% 浏览 + 15% 下单 + 5% 支付） |
| 能发现 | 单点瓶颈（SQL / 代码热点） | 共享资源竞争：连接池互踩、缓存淘汰互挤、下游雪崩 |
| 结论可靠性 | 「这个接口能扛 X」 | 「系统能扛 X」 |

- 只做单接口压测会得出危险结论：查询接口单独能扛 5000 QPS，混入 20% 写流量后锁竞争 + 缓存抖动，3000 就崩。
- 工具选择：**k6**（JS 脚本——你的主场，声明式 stage 渐进加压）、Gatling（代码化场景报告好）、JMeter（老牌全功能、GUI 录制）。一句话推荐：k6 对前端背景最友好（JS 写脚本，上手即用）；Gatling 适合深度定制的团队。

```javascript
// k6 场景压测脚本：流量模型 + 阶段 + 阈值(SLO 即代码, 压测与线上目标同一份定义)
import http from 'k6/http';
export const options = {
  stages: [ { duration: '2m', target: 200 },   // 爬坡到稳态
            { duration: '10m', target: 810 },  // 容量目标(第1节的数)
            { duration: '5m', target: 0 } ],
  thresholds: {
    'http_req_duration{ep:order_create}': ['p(99)<500'],   // 各接口 SLO
    'http_req_failed': ['rate<0.001'],                      // 错误率 0.1%
  },
};
export default function () {
  const r = Math.random();
  if (r < 0.8) http.get(`${BASE}/goods/list`);       // 浏览流量 80%
  else if (r < 0.95) http.post(`${BASE}/order/create`, body, { headers });
  else http.post(`${BASE}/pay/notify`, body);          // 支付回调 5%
}
```

### 3. 全链路压测：不污染线上数据

```text
压测流量与真实流量同走生产链路 —— 三个隔离装置:
① 流量染色: 压测请求打标记(Header X-Load-Test: shadow), 全链路透传(MQ 消息属性也要带)
② 影子表/影子库: 染色写请求改写落到 order_shadow(同构表) —— 真实表零污染
③ 挡板(Mock): 下游第三方(支付/短信/风控)返回预置响应, 不打真实渠道
   + 影子缓存 key 前缀(shadow:) / 影子 topic(Shadow-order-events)
```

- 落地形态：入口网关染色 → 中间件 SDK 统一识别上下文标记 → DB 路由层按标记切影子表 → 消费端同样分流。
- **影子表 DDL 必须与主表同步变更**——纳入发布检查清单：主表加列忘改影子表，压测结果直接失真。
- **影子数据定期清理**——影子表也是真磁盘，别让压测流量把存储吃爆。
- 注意施压端自身：单机 k6 的网卡 / CPU 先成瓶颈会误判——大流量分布式施压，**压测前先压施压机**。

### 4. 三份产出（压测不是跑完就结束）

```text
① 容量水位报告: 各接口/各资源当前水位与极限容量(QPS-RT-错误率拐点曲线)
   → 例: createOrder 拐点 4200 QPS, 当前水位 810 = 19% 安全; stock-query 单实例瓶颈在 Redis 带宽非 CPU
② 扩容预案: 水位到多少触发扩什么(实例数/DB连接/分片) —— 与 HPA 阈值对齐(阶段五第2讲)
   → 例: 应用>70% 水位 → HPA 已管; DB 连接>80% → 预案A扩只读从库, 预案B降缓存穿透开关
③ 降级预案: 极限流量下的取舍清单(保下单/砍推荐/砍评论, 兜底数据 + 有损服务, 阶段六第3讲)
   → 每条带触发条件(错误率>x% 或水位>90%)与执行人, 并且演练过
```

- **降级预案不是电商专属**：中后台系统的降级取舍——保核心 CRUD、砍实时报表与操作日志采集。每个系统都有自己的「保下单」。
- **数据单表 5000w、日增 100w 的六个月演进**（大纲自选题的算术示范）：半年后累计 = 5000w + (100w×180) ≈ 2.3 亿。此时「归档能续命」优先于「分库分表一步到位」——策略：① 冷数据归档（把 6 个月以前的订单迁历史表，主表回落到千万级）；② 读写分离 + 覆盖索引压慢查询；③ 若日增仍 >100w 且查询持续恶化 → 再按 user_id 分片（分片键选最高频查询维度）。核心心法：**归档能续命，就先续命；真到归档也压不住，才分库分表**。

### 坑点提醒

- **拿低峰基线扛大促**：缓存命中率、锁竞争、连接池行为在流量模型下完全不同——容量基线必须在**目标场景模型**下压测得出。
- **压测数据不隔离就撤挡板**：一次全链路压测打穿生产 = 千万假订单 + 真实短信轰炸——影子链路与挡板开关要有双重确认。
- **只看通过/失败不看拐点**：SLO 达标区间、性能拐点、崩溃斜率三个特征点都画进报告——「3000 能跑」和「3500 开始崩、3800 雪崩」是两个决策。
- **HPA 阈值拍脑袋**：扩容触发线必须来自容量水位（70% 水位对应已压测过的极限），不是 80% CPU 的玄学默认。

## 本节配套思考题

1. 「p99 在 400ms 以内」是接口 SLO——大促当天怎么执行它：超了多久、超到什么程度触发降级？SLO 与「一次抖动」的判定边界怎么设计（错误预算）？
2. 影子表的 DDL 变更要和主表同步——半年后它们不一致导致压测结果失真。把「影子链路一致性」纳入哪类日常流程（发布 checklist / CI）才算根治？
3. 你的场景压测发现「下单 + 查询混合时性能骤降，单独都不差」——列三种共享资源竞争假设与各自验证方法（连接池 / 缓存 / 锁）。
