# M2.5-03：RocketMQ 延时关单

返回 [实践计划与进度](../README.md)。

## 目标

订单创建后发送可追踪的延时消息；超时未支付订单自动关闭并释放库存，重复投递不产生重复副作用。

## 范围

- 使用 Apache RocketMQ 5.5.1 普通 Java client；topic、生产组、消费组、NameServer、发送超时、延时等级、轮询批次、重试上限和退避时长全部从配置源读取。
- 定义 `order-timeout` v1 集成事件，包含事件 ID、业务幂等键、订单 ID、版本和创建时间；消息 key 使用稳定业务键，tag 使用版本化事件类型。
- 订单、明细、数据库库存预扣和 Outbox 记录在同一本地事务提交；调度器在事务外发送延时消息，发送成功标记 `SENT`，失败按有界退避重试，超过上限标记 `DEAD` 并记录指标。
- 消费者只把仍为 `CREATED` 的订单改为 `CANCELLED` 并在同一数据库事务释放锁定库存、完成 Outbox；已支付、已取消或已完成订单标记 `IGNORED`，不改变订单与库存。
- 相同事件重复投递由 Outbox 业务键和消费终态幂等吸收；消费异常返回稍后重试，超过配置次数进入 RocketMQ 死信队列。
- 记录发送成功、发送失败、发送终止、消费成功、忽略、重复、重试和处理时延指标；日志携带事件 ID、业务键和订单 ID。

## 契约与最小场景

- 订单 HTTP 创建契约保持不变；MQ 不可用时订单事务仍成功，Outbox 保留待重试事实，不能丢失超时任务。
- 默认延时等级 16 对应 RocketMQ 标准 30 分钟；真实集成测试覆盖等级 1 的 1 秒投递，不用缩短生产默认值。
- 超时未支付订单最终变为 `CANCELLED`，数据库锁定量归零，Redis 预占在数据库提交后释放；已支付订单收到超时事件后保持 `PAID`，库存不回补。
- 同一事件重复消费只产生一次状态迁移和一次库存释放；不存在或载荷不合法的事件拒绝成功确认并进入有界重试。
- 发送失败达到上限后 Outbox 进入 `DEAD`，可通过指标和数据库状态定位；重新投递由运维修复后显式恢复，不在本卡增加管理接口。

## 学习点

集成事件、至少一次投递、幂等消费、延时消息与事务消息一致性。

## 验收

1. 超时未支付订单自动关闭并释放库存，已支付或已关闭订单不受影响。
2. 同一消息重复消费不会重复变更订单或库存。
3. 发送或消费失败可观测，并按既定策略重试或进入失败处置。
4. 真实 RocketMQ 集成测试和全量回归通过。

## 验证命令

按开卡时锁定的 RocketMQ 版本启动真实服务并执行集成测试，再运行 `mvnw.cmd -pl services/user-service -am clean test` 与 `git diff --check`。

## 不做

- 不拆独立订单服务，不引入事件溯源。
- 不实现支付网关、退款或物流业务。
- 不在订单数据库事务内等待 MQ，不依赖恰好一次投递，不用 MQ 事务消息替代本地 Outbox。
