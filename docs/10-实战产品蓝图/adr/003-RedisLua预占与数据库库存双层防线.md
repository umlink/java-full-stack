# ADR-003：Redis Lua 预占与数据库库存双层防线

日期：2026-10-10
状态：已采纳

## 决策

M2.5-02 在 `inventory` 模块增加可关闭的 Redis 预占适配器。每个 SKU 使用 `bootmall:inventory:stock:{skuId}` Hash 保存数据库可用量的性能副本和预占状态；下单先以 Lua 原子校验并扣减 Redis 可用量，再在订单本地事务中执行原有数据库条件更新。数据库中的 `total_count`、`locked_count`、检查约束和条件更新始终是交易事实与最终防线。

预占 ID 由用户作用域和下单幂等键生成稳定 SHA-256 值。相同 ID、SKU 和数量的并发请求共享一次扣减，并以待处理尝试计数防止一个失败请求释放另一个仍在执行的请求；相同 ID 与不同数量被判为冲突。数据库事务成功后把 Redis 状态标为已确认，失败则减少尝试计数，最后一个失败尝试负责回补可用量。支付实扣不改变可用量，取消释放在数据库事务提交后用幂等 Lua 回补。

Redis 是可重建性能副本。连接或脚本失败时记录 `bootmall.inventory.redis.reservations` 指标并降级到数据库条件更新，保持既有订单行为。Redis 已执行但客户端未收到结果、提交后同步失败等不可判定窗口允许形成短暂差异，由 M2.5-04 对账任务按数据库事实修复。

M2.5-04 的对账按 SKU 主键游标分批读取数据库，权威可售量为 `total_count - locked_count`。Redis key 缺失允许下一次请求惰性重建；值不一致或损坏时使用原子 Lua 删除整个 SKU Hash，而不直接覆盖 `_available`，避免遗留预占字段与新可售量组合成不一致状态。并发窗口中删除只会降低缓存命中，任何重新预占仍必须通过数据库条件更新，因此不会绕过最终库存约束。

## 触发信号与备选

M2.5 要求用 Lua 展示库存原子预扣、同键幂等、数据库失败补偿和并发不超卖，同时保留 M2 已验证的数据库最终约束。

- 继续只用数据库条件更新：一致性简单且当前已经正确，但无法在数据库之前快速削峰，也没有交付 Lua 原子预占学习目标。
- 只信任 Redis 并异步落库：吞吐更高，但当前没有可靠事件链路与对账闭环，Redis 丢失或消息失败会直接破坏交易事实。
- Redis 预占加数据库最终确认：保留原事务边界和回退路径，代价是需要幂等状态、补偿指标和后续对账。

## 影响与回退

开启 `BOOT_REDIS_INVENTORY_ENABLED` 后，Redis 低可用量可以提前拒绝请求，数据库仍会对每个成功预占执行条件更新。管理员设置库存后删除对应 Redis key；key 过期或缺失时从数据库当前可用量初始化。

关闭 `BOOT_REDIS_INVENTORY_ENABLED` 并重启即可回到原数据库条件更新路径，无需迁移数据库。Redis 中残留的是可重建副本和幂等状态，可按前缀清理；回退不会改变订单、库存表或公开 HTTP 契约。
