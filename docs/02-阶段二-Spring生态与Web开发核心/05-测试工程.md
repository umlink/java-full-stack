# 阶段二 · 小点 5：测试工程（贯穿全程）

> 所属：阶段二 Spring 生态与 Web 开发核心
> 定位：测试不是附属技能，是工程能力的核心指标。你写过 Jest + Supertest，概念可全量迁移；这里建立 Java 侧工具链与分层策略，并从阶段二起贯穿到所有实战项目——**测试不过就不许合并**是后面项目的流水线门禁。

## 快速入门

> 本节为「测试速览」：先认识 Java 测试的几件工具、各自干什么；「切片取舍、Testcontainers」留在正文提高部分。

### 本讲核心关键词速查

| 关键词 | 一句话大白话 | 例子 |
|-|-|-|
| JUnit 5 | Java 的测试框架（跑单元测试） | `@Test` 标注测试方法 |
| AssertJ | 断言库（更口语化的断言） | `assertThat(x).isEqualTo(42)` |
| Mockito | 造「假对象」的库 | `mock(OrderRepo.class)` |
| mock / stub | 造替身 / 预设返回 | 测 Service 不用真连 DB |
| @SpringBootTest | 启动完整 Spring 上下文的测试 | 集成测试 |
| @WebMvcTest | 只测 Web 层的切片 | 测 Controller |
| Testcontainers | 用真实 Docker 容器做集成测试 | 消灭内存库「假绿色」 |
| 覆盖率 | 测试覆盖了多少代码 | JaCoCo 门禁 |

### 本讲在解决什么问题

- **问题**：不写测试，改一处代码不知道崩没崩。写测试，才知道「这次改动有没有破坏别的地方」。Java 侧用 JUnit + Mockito + Spring Test。
- **你要带走的一句话**：**单元测试**用 Mockito mock 掉依赖（不连数据库，快）；**集成测试**用 SpringBootTest 起真实上下文；**要真正接近生产**用 Testcontainers 起真实容器——分三种粒度各司其职。

### 最简可运行示例（照抄能跑）

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.*;
import org.mockito.junit.jupiter.MockitoExtension;
import static org.assertj.core.api.Assertions.assertThat;
import static org.mockito.Mockito.*;

@ExtendWith(MockitoExtension.class)         // 启用 Mockito 注解
class OrderServiceTest {

    @Mock OrderRepository repo;              // 造一个假的 repo
    @InjectMocks OrderService service;       // 把假 repo 注入被测类

    @Test
    void create() {
        when(repo.save(any())).thenReturn(1L);   // 预设: 调用 save 返回 1
        Long id = service.create(...);
        assertThat(id).isEqualTo(1L);            // 断言结果
        verify(repo).save(any());                // 验证确实被调用了
    }
}
```

> 代码备注（逐行解释）：
> - `@ExtendWith(MockitoExtension.class)`：启用 Mockito 的注解功能。
> - `@Mock OrderRepository repo`：造一个**假的**仓库对象，测试里不真连数据库。
> - `@InjectMocks OrderService service`：把假 repo 注入到被测的 Service 里。
> - `when(repo.save(any())).thenReturn(1L)`：**stub**——告诉假对象「你被调用时返回 1」。
> - `assertThat(id).isEqualTo(1L)`：AssertJ 断言，比 JUnit 自带的更口语化。
> - `verify(repo).save(any())`：验证这个方法**确实被调了**——测「行为」而不仅是结果。

### 关键注解 / 工具说明

| 注解 / 工具 | 干什么 | 最易踩的坑 |
|-|-|-|
| `@Test` | 标注测试方法 | 测试方法要 `public` 且无参 |
| `@Mock` / `@InjectMocks` | 造假对象 / 注入被测对象 | mock 默认返回 null/0，要 `when` 预设 |
| `@WebMvcTest` | 只测 Web 层 | 会 mock 掉 Service，注意 |
| `@DataJpaTest` | 只测数据层 | 默认用内存库，注意和生产的差异 |
| `@SpringBootTest` | 起完整上下文 | 最慢，别滥用 |
| `@MockitoBean`（新）/ `@MockBean`（旧） | 集成测试替换 Bean | 用新注解，旧的 Boot 3.4 起废弃 |

### 常用约定 / 命名提示

- **测试命名**：`*Test` 单测（surefire 跑）、`*IT` 集成测试（failsafe 跑）——命名即运行粒度。
- **测试金字塔**：底层大量单元测试（快）、中层少量集成、顶层极少端到端（慢）。别全用 `@SpringBootTest`（又慢又重）。
- **覆盖率门禁分层**：手写核心业务规则 ≥70%，自动生成代码 ≥50%——别对生成代码也压同样的门槛。
- **别用内存库冒充生产**：H2 测试过 ≠ 生产能用（方言、索引差异）——关键路径用 Testcontainers 起真库。

## 精简大纲

1. JUnit 5：生命周期 / 参数化 / AssertJ
2. Mockito：mock / stub / verify 与边界
3. Spring Test 切片：@WebMvcTest / @DataJpaTest / @SpringBootTest 的取舍
4. Testcontainers：真实容器替代内存库的「假绿色」
5. 覆盖率门禁与测试金字塔
6. E2E 端到端：验证「用户最终用到的链路」

## 学习内容详情

### 1. JUnit 5

```java
import org.junit.jupiter.api.*;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import static org.assertj.core.api.Assertions.*;

class DiscountServiceTest {

    @BeforeEach
    void setUp() { /* 每个用例前重建被测对象——保证用例间零污染 */ }

    @Test
    void memberGetsDiscount() {
        var price = discountService.calc(100, MemberType.GOLD);
        assertThat(price).isEqualTo(80.0)            // AssertJ 流式断言: 失败信息是「expected 80.0 but was 90.0」
                .isGreaterThan(0.0);                 // 可读性即维护性 —— 别用裸 assertEquals
    }

    @ParameterizedTest(name = "原价 {0} 应收 {1}")      // 表驱动: go test 的参数化 / Jest 的 test.each
    @CsvSource({ "100, 80", "0, 0", "999, 799.2" })
    void calcTable(int input, double expected) {
        assertThat(discountService.calc(input, MemberType.GOLD)).isEqualTo(expected);
    }
}
```

- 生命周期：`@BeforeAll`（类级，须 static）→ `@BeforeEach` → `@Test` → `@AfterEach` → `@AfterAll`；`@Disabled` 标注跳过（**要带理由注释**）。

### 2. Mockito

```java
import org.mockito.*;
import static org.mockito.Mockito.*;

class OrderServiceTest {
    @Mock OrderRepository repo;                 // 造一个"假仓库": 不连数据库
    @Spy  PriceCalculator calc = new PriceCalculator();   // 真对象 + 可拦截观察
    @InjectMocks OrderService service;          // 把上面的 mock 注入被测对象的构造器

    @Test
    void stockInsufficient_nothingSaved() {
        when(repo.findById(1L)).thenReturn(Optional.empty());        // stub: 预演"查不到"分支
        assertThatThrownBy(() -> service.create(1L, 2))
                .isInstanceOf(OrderNotFoundException.class);
        verify(repo, never()).save(any());                           // 验证: 失败路径上绝不能落库
        verifyNoMoreInteractions(repo);                              // 行为回归: 没多干别的事
    }
}
```

- 三板斧：`when().thenReturn()`（stub）/ `verify()`（验证交互）/ `ArgumentCaptor`（抓参数细节）。
- **边界认知**：`mockStatic` / `mockConstruction` 能做但克制——需要大量 mock 静态方法通常说明设计耦合过重，该重构接缝而不是 mock 它。
- 与 Jest `jest.fn()` / `mockReturnValue` 完全同构，概念零成本迁移。

### 3. Spring Test 切片（按需启动容器的一部分）

```java
@WebMvcTest(OrderController.class)      // 只装配 Web 层: Controller + 过滤器/转换器; Service 自动 mock
class OrderControllerTest {
    @Autowired MockMvc mvc;             // 不用真起 HTTP 端口, 模拟请求进 DispatcherServlet
    @MockitoBean OrderService service;  // 下游依赖给个哑元
    // 注: 老代码里的 @MockBean 自 Boot 3.4 起废弃（新版本已移除）, 统一改用
    // spring-test 提供的 @MockitoBean —— 语义一致, 注解换个包名

    @Test
    void invalidBody_returns400() throws Exception {
        mvc.perform(post("/api/v1/orders").contentType(APPLICATION_JSON).content("{}"))
           .andExpect(status().isBadRequest())
           .andExpect(jsonPath("$.code").value(40001));
    }
}
```

| 注解 | 加载范围 | 适用 |
|-|-|-|
| `@WebMvcTest` | 仅 Web 层 + Mock Service | 参数绑定 / 状态码 / 校验规则 |
| `@DataJpaTest` | 仅持久层 + 测试库 | Repository 查询正确性 |
| `@SpringBootTest` | 全容器 | 端到端集成 / 装配验证 |

- 取舍原则：**能切片不全量**——测试速度决定跑的频率，跑的频率决定测试的存活。全量启动的套件超过 30 秒，人就开始「先不跑了」。

### 4. Testcontainers：集成测试不撒谎

```java
@Testcontainers
class OrderRepositoryIT {                  // IT 后缀: 集成测试, CI 单独阶段跑

    @Container                             // 整个测试类共享一个真 MySQL 容器(@Container 静态字段)
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.4")
            .withDatabaseName("shop")
            .withInitScript("schema.sql"); // 真实 DDL 也参与测试 —— 建表语句写错当场暴露

    @DynamicPropertySource                  // 把容器的随机端口注入 Spring 配置
    static void props(DynamicPropertyRegistry r) {
        r.add("spring.datasource.url", mysql::getJdbcUrl);
    }

    @DataJpaTest
    void jsonColumn_roundTrips() {
        // H2 没有 JSON 列类型 → 内存库时代这测试「假绿」; 真 MySQL 立刻教做人
        var saved = repo.save(new Order(payloadJson));
        assertThat(repo.findById(saved.getId()).orElseThrow().getPayload()).isEqualTo(payloadJson);
    }
}
```

- **本质优势**：行为一致性（方言 / JSON 函数 / 隔离级别差异在测试期就暴露）——**不是「快」，它甚至更慢**；换来的是「测试通过 ≈ 生产可用」的可信度。
- 成本对策：容器静态共享 + 复用（Testcontainers Reuse），别每个用例起一个。
- **命名即运行粒度**：`*Test` 单测/切片由 surefire 跑，`*IT` 集成测试由 failsafe 跑——CI 按此分层（上面 `OrderRepositoryIT` 的后缀就是给 failsafe 认的）。

第三方 HTTP 依赖（支付 / 短信 / 下游接口）的标准挡板是 **WireMock**——比真调沙箱快且稳定：

```java
stubFor(get(urlEqualTo("/price/1001"))                  // 请求进来先精确匹配路径
        .willReturn(aResponse().withStatus(200).withBody("{\"price\": 99}")));
// WireMock 的端口同样用 @DynamicPropertySource 注进被测服务的 baseUrl, 下游行为完全可控
```

### 5. 覆盖率与测试金字塔

```xml
<!-- JaCoCo: 覆盖率报告 + 门禁(低于阈值构建直接失败) -->
<plugin>
    <groupId>org.jacoco</groupId><artifactId>jacoco-maven-plugin</artifactId>
    <executions>
        <execution><id>check</id><goals><goal>check</goal></goals>
            <configuration><rules><rule>
                <limits><limit>
                    <counter>BRANCH</counter><value>COVEREDRATIO</value>
                    <minimum>0.70</minimum>          <!-- 分支覆盖 ≥70%: 数字是起点, 趋势比达标更重要 -->
                </limit></limits>
            </rule></rules></configuration>
        </execution>
    </executions>
</plugin>
```

- 覆盖率是「没测试的探测器」，不是「质量的证明」——**行覆盖了、断言为空**是刷分典型（`assertTrue(true)` 式测试），评审时盯断言有效性，不只看百分比。
- **测试金字塔**：单元（多 / 快 / 稳，秒级）→ 集成（中 / 真实依赖，Testcontainers）→ E2E（少 / 贵 / 慢）。倒金字塔（E2E 一堆）= 架构警报：CI 半小时、偶发红、没人敢改。

### 6. E2E 端到端：验证「用户最终用到的链路」

> 单元测 Service、集成测 Repository + 真实容器，但**用户用的是「前端 → 接口 → 数据库」整条链路**。E2E 就是模拟真实用户在浏览器/客户端走过完整流程——它少而贵，只覆盖**最关键的用户旅程**（如「下单成功」「登录→看到订单」）。

```javascript
// Playwright 端到端(前端出身最顺手): 模拟真实用户走一遍下单流程
import { test, expect } from '@playwright/test';

test('用户能完成下单', async ({ page }) => {
    await page.goto('/');                         // 打开首页
    await page.click('text=加入购物车');           // 真实点击, 不是调接口
    await page.click('text=去结算');
    await page.fill('#address', '上海');           // 填真实表单
    await page.click('text=提交订单');
    await expect(page).toHaveURL(/order\/success/);  // 断言跳到成功页
});
```

> 说明（逐条解释）：
> - E2E **模拟真实用户操作**（点击、填表、跳转），用的是浏览器（Playwright/Cypress），不是直接调接口。
> - 它测的是**整条链路**——前端页面、接口契约、后端逻辑、数据库全串起来，是金字塔顶端「少而贵」的那一层。
> - **少**：只覆盖最关键的用户旅程（登录、下单、核心流程），别把每个接口都写 E2E（那是倒金字塔）。
> - **贵**：跑得慢、依赖完整环境、易偶发红——所以放 CI 的**主干级**（阶段五 CI/CD），MR 级只跑快测。
> - Java 侧配合：前置准备数据（Testcontainers 起真库），E2E 针对真实部署的 staging（阶段五第 3 讲），不是本地内存库。

### 坑点提醒

- **Mock 一切 = 测了个寂寞**：被测对象的协作全 mock 掉，测试只验证了「mock 会按 stub 返回」；至少留一路真实集成测试兜底。
- **测试依赖执行顺序**：共享静态状态 / 真库数据不隔离，单跑全绿、全跑翻红——`@DirtiesContext` / 每用例自带 fixture 治它。
- **切片测试里 `@MockitoBean`（旧 `@MockBean`）忘配返回值**：默认返回 null 的 stub 会让 NPE 伪装成「业务 bug」，排查半天——显式 stub，哪怕 `thenReturn(Optional.empty())`。
- **CI 门禁只在合并时跑全量**：主干要快速反馈（单元 + 切片），MR 阶段跑 IT + 覆盖率——金字塔也分层到流水线。
