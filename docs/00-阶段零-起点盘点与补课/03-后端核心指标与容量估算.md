# 阶段零 · 小点 3：后端核心指标与容量估算

> 所属：阶段零 起点盘点与补课
> 定位：补齐「服务端通用心智」的缺口。QPS / TPS / RT / 并发数这些指标是**与语言无关**的——不管你是写 NestJS 还是 Spring，面试被问「这个系统能抗多少 QPS」、上线前被问「要开几台机器」，靠的都是这套估算方法。本小点在正式进入 Java 前先把这层「服务端地基」打牢。

## 快速入门

> 本节为「概念速览」：先认识后端同学常挂在嘴边的几个指标，以及它们和你前端已有心智的对应关系。

### 核心指标速查

| 指标 | 一句话大白话 | 和你已有的对应 |
|-|-|-|
| QPS（每秒请求数） | 系统每秒能处理多少个请求 | 类比 CDN / 网关的每秒命中量 |
| TPS（每秒事务数） | 每秒能完成多少个「完整业务」 | 比 QPS 更严——一个事务可能含多次请求 |
| RT（响应时间） | 一个请求从发出到返回花了多久 | 类比前端的接口耗时 / LCP |
| 并发数（在途请求） | 同一时刻「正在处理」的请求有多少 | 类比浏览器最大并发连接数（6 个） |
| 吞吐量 | 单位时间处理的总量（QPS/TPS 都是它） | 类比 Node 事件循环的每秒处理能力 |
| TP99（99th Percentile） | 99% 的请求 RT 都小于这个值——分位数指标，专门看长尾 | 类比前端「P75 / P95 性能基线」 |

### 服务端估算的三步法

1. **定业务量**：日请求量 / 日活用户 → 算出峰值 QPS。
2. **定单机能力**：用「并发 = QPS × RT」判断瓶颈，再用压测拿真实单机上限。
3. **定机器数**：`机器数 = 峰值 QPS ÷ 单机 QPS × 冗余系数`。

### 最容易搞混的三个点

- **QPS 不是并发数**：并发数 = QPS × RT。RT 100ms、QPS 1000 时，同一时刻在途请求只有 100 个——「每秒 1000 个」和「同时在跑 100 个」是两个概念，混了容量就算错。
- **别拿平均 RT 当真相**：平均 RT 会掩盖长尾。100ms 的均值可能是 50ms 的 90% 请求 + 550ms 的 10% 慢请求算出来的——要看 TP99 / TP999。
- **别拿平均 QPS 当峰值**：一天 86400 秒，日请求量除以 86400 得到的是「平均」，峰值通常是平均的 4~10 倍（业务有明显波峰波谷时更高）。

### 本阶段你该做到

- [ ] 能口算：RT 200ms 的接口，想扛 5000 QPS 需要多少并发？
- [ ] 能反推：日均 100 万请求的业务，峰值 QPS 大概是多少量级？
- [ ] 知道 TP99 是什么、为什么比平均 RT 重要
- [ ] 知道「压测」拿到的单机 QPS 该怎么用于估算机器数

### 一句话总结

> 后端容量估算的本质是「**业务量 → 指标 → 资源**」的一条换算链：用利特尔定律（并发 = QPS × RT）把三件事串起来，先估算、再压测验证。这套心智与语言无关，是 Java 后端学习中最先能「复用」的部分。

## 学习内容详情

### 1. 四大核心指标

- **QPS（Queries Per Second，每秒查询数）**：系统每秒能处理的请求数。互联网语境下常把 QPS 当作「每秒请求数」的通用说法（RPS，Requests Per Second），两者混用但含义一致。
- **TPS（Transactions Per Second，每秒事务数）**：每秒完成的「完整业务事务」数。一个事务可能跨多次请求（如「下单」= 校验 + 扣库存 + 记账 + 发消息），所以 **TPS 更能反映业务真实处理能力**。电商场景看 TPS，纯查询场景看 QPS。
- **RT（Response Time，响应时间）**：从请求发出到响应返回的时间。**一定配百分位看**：TP50（中位数）、TP95、TP99、TP999。TP99 = 100ms 表示「99% 的请求在 100ms 内返回」，剩下 1% 是长尾——长尾往往才是用户真正骂的慢。
- **并发数（在途请求数）**：某一时刻正在处理中的请求总数。**注意**：它不是一个「指标」，而是 QPS 与 RT 的乘积（见第 2 节）——这也是为什么有人把系统压崩时看起来「每秒也没多少请求」，因为 RT 被拖长、在途请求在暴涨。

```text
// 记住这三组单位：
QPS 单位：req/s（每秒多少个）
RT  单位：ms / s（每个花多久）
并发  单位：个（同时多少个在跑）
```

### 2. 利特尔定律：并发数 = QPS × RT ⭐

这是本小点（乃至整个容量估算）最重要的公式，来自排队论（Little's Law），对任何稳定系统都成立：

```text
在途并发数 = QPS × RT

推导：
QPS = 并发数 ÷ RT
RT  = 并发数 ÷ QPS
```

**理解**：系统就像一个流水线，QPS 是「每秒进多少件」，RT 是「每件在线上待多久」，并发数是「线上同时在处理几件」。

**口算练习**：

| 场景 | 计算 | 结果 |
|-|-|-|
| RT 200ms，QPS 5000 | 5000 × 0.2s | 并发 1000 |
| RT 100ms，扛 1000 并发 | 1000 × 0.1s | QPS 10000 |
| QPS 800，并发 400 | 400 ÷ 800 | RT 0.5s（500ms）|

**工程含义**：

- **RT 涨一倍，并发需求翻倍**：同样是 5000 QPS，RT 从 100ms 涨到 200ms，并发数就从 500 涨到 1000——线程/连接池不够就排队，排队又拉长 RT，恶性循环（这就是「雪崩」的微观机制）。
- **为什么 Node 单线程也能高并发**：因为它把 RT 里的「等待 IO 时间」释放出去了，实际占用线程的时间极短，等价于「并发 = QPS × 有效处理时间」——这个心智在学 Java 虚拟线程（阶段 1）时会再次用到。

### 3. 业务量反推：从 DAU 到峰值 QPS

拿不到真实压测数据时，先用量级估算确定「系统该按什么量级设计」：

```text
平均 QPS = 日总请求量 ÷ 86400（一天秒数）
峰值 QPS ≈ 平均 QPS × 峰值系数（一般 4~10 倍）

// 换算起点常来自业务口径：
// DAU（Daily Active Users, 日活）× 人均请求数 = 日总请求量
// PV（Page View）/ UV（Unique Visitor）是 C 端产品口径，与 DAU 配合使用
```

| 业务规模 | 日总请求量 | 平均 QPS | 峰值 QPS（按 5 倍估）| 量级判断 |
|-|-|-|-|-|
| 小型内部系统 | 10 万 | ~1.2 | ~6 | 单机绰绰有余 |
| 中型业务 | 1000 万 | ~116 | ~580 | 需要多机 + 缓存 |
| 大型业务 | 1 亿 | ~1157 | ~5800 | 需要缓存 + 集群 + 限流降级 |

**细化峰值系数**：有典型「晚高峰」的 C 端业务（如 19:00-22:00 贡献全天 60% 流量），峰值系数取 8~10；B 端 / 全天均匀的业务取 3~5。更精确可以按「小时分布」算：先估最高小时流量，再 ÷ 3600。

### 4. 容量估算：从峰值 QPS 到机器数

```text
所需机器数 = 峰值 QPS ÷ 单机 QPS × 冗余系数（建议 1.5~2 倍）

冗余系数说明：
× 1.5~2  ≈ 预留故障转移（挂一台不垮）+ 突发流量缓冲
```

**单机 QPS 从哪来**——两条路，缺一不可：

1. **先理论粗估**（下界）：单机 QPS ≈ 可用并发 ÷ RT。8 核 16G、Tomcat 默认 200 线程，纯逻辑接口 RT 20ms → 粗估单机 ~5000~10000 QPS（但这只是乐观上界）。
2. **再压测实测**（真实值）：用压测工具（第 5 节）打到 CPU 80% 或 RT 开始明显抬升的那个点，才是可信的单机 QPS。**估算定数量级，压测定最终数字。**

**容量不是越多越好**：机器多了成本高、运维重；机器少了高峰期 RT 雪崩。正确姿势是「按峰值 + 冗余」配好，再靠**弹性伸缩**（阶段 5 云原生）应对突发。

### 5. 压测与指标解读

**常用压测工具**：

| 工具 | 场景 | 特点 |
|-|-|-|
| `ab`（Apache Bench） | 单接口快速冒烟 | 命令行一条命令，够粗 |
| `wrk` / `wrk2` | 单机高性能压测 | 基于 C，能压出几十万 QPS，wrk2 支持设定目标 RT 分布 |
| JMeter | 复杂业务链路压测 | 图形化、支持多接口串联、断言与报告 |
| Gatling / k6 | 脚本化压测 | 代码即脚本，适合进 CI |

> ⏸️ **短期可以不学（压测工具的进阶用法）**：JMeter 复杂场景编排、Gatling 的 Scala DSL、k6 扩展开发等不必投入——会用一款工具打出流量、看懂下面四个核心指标即可，工具之间的迁移成本很低。**何时回来学**：要做全链路压测或把压测纳入 CI 流水线时。**面试最低要求**：考察点永远在「压测看什么指标、瓶颈怎么定位」，不在「会用哪个工具」。

**压测必须看的四个数**（只看 QPS 是外行）：

1. **QPS / TPS**：吞吐够不够。
2. **RT 分位**：QPS 上去后 TP99 是否仍达标（一般要求 TP99 < 某阈值，如 500ms）。
3. **错误率**：5xx / 超时占比——压测时 QPS 很好看但错误率 20% 就是自欺欺人。
4. **资源水位**：CPU、内存、线程数、连接数、GC 频率——找到真正瓶颈在哪（是线程池满了，还是数据库慢，还是 GC 频繁）。

**典型瓶颈排查顺序**：应用线程 → 连接池（DB/Redis）→ 外部依赖 RT → GC → 磁盘/网络 IO。阶段 1（JVM）与阶段 3（MySQL/Redis）会逐层深入。

### 6. 实战演练：电商「秒杀」容量估算

**场景**：某电商 20:00 开启秒杀，预估 1 小时内产生 360 万次请求。

```text
① 峰值 QPS
   360 万 ÷ 3600s = 1000 平均 QPS
   秒杀前 1 分钟流量最猛，按 3 倍尖峰 → 峰值约 3000 QPS

② 单机能力
   下单链路含 DB + 库存校验，RT 约 300ms
   乐观粗估：并发 200 ÷ 0.3s ≈ 666 QPS/单机
   压测实测：假设 400 QPS/单机（RT 100ms 内达标）

③ 机器数
   3000 ÷ 400 × 1.5 冗余 ≈ 12 台

④ 关键决策点（比算数更重要）
   - 秒杀链路必须走「预扣库存 + 缓存 + 限流」，不能让全部流量打到 DB
   - 12 台是「扛住」的下限，真正的设计目标是「削峰」：队列削峰、提前放量
   - 如果不想上 12 台，可以限流把峰值压到 1000 QPS——容量估算和流量治理是一体两面
```

> 这个案例的完整解法（缓存、限流、削峰、异步化）会在阶段 3（Redis / 消息队列）与阶段 6（高可用架构）正式展开——本小点先让你「算得清账」，后面再教你「怎么省这笔账」。

## 配套练习（自测）

1. 接口 RT 平均 250ms、TP99 800ms，目标峰值 2000 QPS，估算需要多少并发，并说明为什么平均 RT 在这里不够用。
2. 日活 50 万、人均每天触发 20 次请求，业务有典型晚高峰，估算峰值 QPS 与大致需要的服务实例数（假设压测单机 1000 QPS）。
3. 压测结果：单机 2000 QPS、CPU 40%、RT 正常；继续加压到 5000 QPS 时 RT 飙到 2s、错误率 15%。分析最可能先查哪一层瓶颈，为什么。

> 参考答案思路：① 并发 = 2000 × 0.25 = 500，但 TP99 800ms 说明长尾请求占用的在途并发远高于均值推演，需按 TP99 重算上限并优先治理长尾；② 50 万 × 20 ÷ 86400 ≈ 116 平均 QPS，晚高峰按 8 倍 ≈ 926 峰值 QPS，机器 ≈ 926 ÷ 1000 × 1.5 ≈ 2 台（但单点风险大，实际至少 3~4 台）；③ 先查线程池/连接池是否打满（RT 从均值级跳到秒级，最典型是排队），再查下游 DB/Redis 连接与 GC。

## 常见面试题

### Q1：QPS、RT、并发数三者是什么关系？

**答**：标准结论：利特尔定律（Little's Law）——**并发数 = QPS × RT**，三者知二推一。例如 RT 200ms 扛 5000 QPS，在途并发就是 1000。原理层：它来自排队论，对任何稳定系统成立——系统像流水线，QPS 是每秒进多少件、RT 是每件在线上待多久、并发数是线上同时在处理几件。工程层的两个关键推论：① **RT 与容量强耦合**——RT 翻倍，同样 QPS 所需的并发资源翻倍，线程/连接池不够就排队，排队又拉长 RT，这就是雪崩的微观正反馈；② 反向定位——线上「吞吐没涨但 RT 飙了」，用并发 = QPS × RT 反推在途请求是否暴涨，能快速判断是「量真大了」还是「某层在排队」。

### Q2：一个日活 100 万的 App，后端要按多少 QPS 设计？怎么估服务器数量？

**答**：标准结论：先估流量再定容量——日活 100 万、人均每天 20 次接口调用 → 日请求量 2000 万 → 平均 QPS ≈ 2000 万 ÷ 86400 ≈ 231；C 端晚高峰业务按 5~8 倍峰值系数 → 峰值 QPS 约 1200~1800；机器数 = 峰值 QPS ÷ 单机 QPS × 冗余系数 1.5~2。若压测单机 800 QPS，则约 1800 ÷ 800 × 1.5 ≈ 4 台起。原理层：峰值系数不是拍脑袋——按小时流量分布算（典型 C 端 19:00-22:00 贡献全天过半流量），B 端/全天均匀业务取 3~5 倍即可。工程层的三个现实修正：① 单机 QPS 必须来自压测（理论估算只是乐观上界，压到 CPU 80% 或 RT 抬升拐点才算数）；② 估算定数量级、压测定最终数字；③ 算容量与做治理（缓存、限流、削峰）是一体两面——不想加机器，就压低真实到达 DB 层的 QPS。

### Q3：为什么平均 RT 不能反映真实体验，要看 TP99/TP999？

**答**：标准结论：平均值会被大量快请求稀释，掩盖长尾——TP99 = 100ms 表示 99% 的请求在 100ms 内返回，剩下 1% 比这更慢。原理层：RT 分布典型呈**长尾（右偏）分布**而非正态——绝大多数请求走缓存命中路径（如 5ms），少数打到慢路径（锁等待、GC 停顿、回源），均值对尾部完全不敏感。举个数字：90% 请求 50ms + 10% 请求 550ms，平均只有 100ms——看起来达标，但每 10 个用户就有 1 个等半秒以上。工程层：① SLO/SLA 全部按分位数定义（如「TP99 < 500ms」），阿里规约也要求接口监控上报分位数而非均值；② 容量估算要用 TP99 而非均值反演并发上限（利特尔定律里的 RT 用分位数，否则低估资源需求）；③ 治理长尾的常见抓手：慢查询、GC 停顿、锁竞争、连接池排队、慢下游——这也是为什么大厂监控面板上 TP999 旁边的毛刺往往就是一次 Full GC。

### Q4：怎么做一次有效的压测？只看压出来的 QPS 高不高行吗？

**答**：标准结论：不行。有效压测必须同时盯四个数——QPS/TPS（吞吐）、RT 分位数（TP99 是否达标）、错误率（5xx/超时占比）、资源水位（CPU、内存、线程数、连接池、GC 频率）。原理层：QPS 单独看是自欺欺人的典型——把超时阈值调大可以在 RT 恶化的情况下「压出」很高的 QPS，但服务实际已经不可用；单机 QPS 的可信定义是「在 RT 与错误率约束下能稳定承载的吞吐」，一般取 CPU 到 80% 或 TP99 开始抬升的拐点。工程层：① 压测环境要逼近生产（同等规格、预热、真实数据量——百万级表的索引表现和空表完全不同）；② 压测前明确目标（验证容量？找瓶颈？回归对比？），不同目标看不同指标；③ 找到瓶颈的排查顺序：应用线程 → 连接池（DB/Redis）→ 下游依赖 RT → GC → 磁盘/网络 IO——压测报告的结论应该是「瓶颈在 X 层」，而不是「能扛 N QPS」。
