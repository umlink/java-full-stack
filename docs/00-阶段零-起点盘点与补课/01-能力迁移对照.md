# 阶段零 · 小点 1：能力迁移对照

> 所属：阶段零 起点盘点与补课
> 定位：在正式开始前，先盘点你的既有能力对 Java 后端学习的直接迁移。这一阶段预计 1-2 周，目标是「环境就绪、路径清晰」。核心结论：你的前端 / Node / Go 经验对 Java 学习的迁移价值远比想象中大——但迁移的是**心智模型**，重学的是**语法与生态**。

## 快速入门

> 本节为「进入 Java 前的热身」：先用你熟悉的前端 / Node / Go 心智，快速认识 Java 后端整套生态长什么样、和你已有的东西如何对应。

### 本讲核心关键词速查

| 概念 | 一句话大白话 | 和你已有的对应 |
|-|-|-|
| Java 后端生态 | 一套「用 Java 写服务器」的软件家族（Spring 全家桶） | 类似 Node 的 Express/NestJS 生态 |
| JVM（Java 虚拟机） | 跑 Java 程序的「引擎」，负责把字节码变成机器码执行 | 类比 Node 的 V8 引擎 |
| Spring 框架 | Java 后端事实标准，负责对象管理、数据库、接口、安全 | 类比 NestJS 框架 |
| Maven | Java 的包管理 + 构建工具 | 类比 npm + vite 打包 |
| 注解（Annotation） | 写在类/方法上的标签——但注解本身只是元数据、不含逻辑，行为由框架在运行期通过反射读取并织入 | 类比 TS 的装饰器（形似神不似，见坑点提醒） |
| 依赖注入（DI, Dependency Injection） | 框架把依赖「递」给你，你不用自己 new——它是控制反转（IoC, Inversion of Control）思想的落地实现 | 与 NestJS 的 DI 同源 |
| 多线程 / 并发 | 同时处理很多请求 / 任务的机制 | 类比 Go 的 goroutine、Node 的事件循环 |
| 虚拟线程 | Java 新版轻量线程，能扛海量 IO 并发 | 类比 goroutine |

### 本讲在解决什么问题

- **问题**：不知道自己「会什么、缺什么」——不知道哪些经验能直接复用（可以加速通过）、哪些是看似会实则要重学的雷区（必须投入时间），学习计划就没法排。
- **你要带走的一句话**：你不是从头学 Java，而是**把已有的服务器端心智，迁移到 Java 语法上**——心智模型是通用资产，语法与生态是记忆成本。本小点就是帮你把这张「心智地图」画出来。

### 最简可运行示例（照抄能跑）

同一个「把依赖的创建交给框架」的心智，两种语法皮肤——左边是你熟悉的 NestJS，右边是对应的 Spring，逐行对齐着读：

```typescript
// NestJS: @Injectable 声明可注入，构造器注入
@Injectable()
export class OrderService {
  constructor(
    private readonly repo: OrderRepository,   // 框架自动装配
  ) {}

  async create(dto: CreateOrderDto) {
    return this.repo.save(dto);
  }
}
```

```java
// Spring: @Service 声明可注入，构造器注入（单构造器可省 @Autowired）
@Service
public class OrderService {

    private final OrderRepository repo;        // 框架自动装配

    public OrderService(OrderRepository repo) { // Spring 5 起推荐构造器注入
        this.repo = repo;                      // 字段可 final —— 不可变、便于测试
    }

    public Order create(CreateOrderDto dto) {
        return repo.save(dto);
    }
}
```

> 读到这段你应该有底气了：**NestJS 的装饰器体系本来就是照着 Spring 设计的**——迁移成本主要在「名字对不上」，不在「概念想不通」。路由、校验等更多对照见正文第 2 节。

### 2. 同构代码对照：NestJS vs Spring

**依赖注入**——同一个「把依赖的创建交给框架」的心智，两种语法皮肤：

```typescript
// NestJS: @Injectable 声明可注入，构造器注入
@Injectable()
export class OrderService {
  constructor(
    private readonly repo: OrderRepository,   // 框架自动装配
  ) {}

  async create(dto: CreateOrderDto) {
    return this.repo.save(dto);
  }
}
```

```java
// Spring: @Service 声明可注入，构造器注入（单构造器可省 @Autowired）
@Service
public class OrderService {

    private final OrderRepository repo;        // 框架自动装配

    public OrderService(OrderRepository repo) { // Spring 5 起推荐构造器注入
        this.repo = repo;                      // 字段可 final —— 不可变、便于测试
    }

    public Order create(CreateOrderDto dto) {
        return repo.save(dto);
    }
}
```

> 读到这段你应该有底气了：**NestJS 的装饰器体系本来就是照着 Spring 设计的**。`@Injectable()` ≈ `@Service`，`@Module` ≈ `@Configuration + @ComponentScan`，Pipe ≈ Bean Validation。迁移成本主要在「名字对不上」，不在「概念想不通」。

**装饰器路由 vs 注解路由**：

```typescript
@Controller('orders')
export class OrderController {
  @Post()
  @UseGuards(AdminGuard)                 // Guard: 守卫
  create(@Body() dto: CreateOrderDto) { /* ... */ }
}
```

```java
@RestController
@RequestMapping("/orders")
public class OrderController {

    @PostMapping
    @PreAuthorize("hasRole('ADMIN')")    // 方法级安全 ≈ Guard
    public Order create(@Valid @RequestBody CreateOrderDto dto) { /* ... */ }
    // @Valid 触发 Bean Validation ≈ Pipe 校验
}
```

### 3. 迁移学习法的总原则与两个「直觉陷阱」

**先记住一个类比：换驾照。** 你在国内会开车（前端 / Node / Go），现在去国外开车（Java）：方向盘、油门刹车、变道打灯（心智模型）基本一样，你上车就能开；但交规细节、路标文字、车牌规则（语法与生态）得重新背——不背也能开，但罚单（线上事故）会教你怎么做人。**会开车 ≠ 免考驾照**，这正是阶段零存在的意义。

- **概念映射，语法重学**：心智模型直接复用，API 与注解体系重建肌肉记忆——用第 2 节的对照表做「翻译词典」。（就像换驾照：驾驶技术带上，交规重背。）
- **对比 happens-before**：Go 的「不要以共享内存来通信」直觉可迁移，但 Java 的 JMM 是显式规范（阶段一第 5 讲展开）。（就像两国的路权规则大方向一致，细节条文各有各的。）
- **陷阱一：把 `Promise` 微任务语义套到 `CompletableFuture`**——Java 没有「事件循环兜底」，不指定执行器就走公共 ForkJoinPool，IO 任务会饿死它（阶段一第 7 讲）。（就像把「国内绿灯右转默认可以」的习惯直接带到国外——有些地方这是闯灯。）
- **陷阱二：把 goroutine 的成本模型套到平台线程**——Go 开一万个 goroutine 毫无压力；Java 平台线程是重资源必须池化，虚拟线程（JDK 21+）才是对标物。（就像把「小车随便停」的习惯带到限宽的停车位——车是好车，位不是那个位。）

## 坑点提醒

- **别跳过阶段一直奔 Spring**：「NestJS 都会了 Spring 还难吗」的错觉，会栽在 `@Transactional` 失效、类加载、泛型擦除这些底层机制上——Spring 的「魔法」全部构建在阶段一第 3 讲（反射 / 动态代理）之上。`@Transactional` 失效的最小复现是**同类自调用**——调用绕过了代理对象，注解形同虚设：

    ```java
    public void methodA() {              // 外部经代理调用进来
        this.methodB();                  // ❌ this 是原始对象, 绕过代理 → 事务不生效
    }
    @Transactional
    public void methodB() { /* 写库 */ } // 注解形同虚设
    ```
- **别用 JS 的「动态类型」直觉读 Java 泛型**：类型擦除意味着运行时 `List<String>` 与 `List<Integer>` 是同一个类，与 TS 的「类型在编译后消失但开发期全程护航」体感相似，但通配符 PECS 是 TS 没有的深水区。

    > ⏸️ **短期可以不学**：通配符与 PECS（Producer Extends, Consumer Super）在业务代码中使用频率极低，多数团队规范甚至避免复杂通配符。**何时回来学**：阅读 JDK / 开源框架源码遇到泛型签名时。**面试最低要求**：能说清「类型擦除：运行时 `List<String>` 与 `List<Integer>` 是同一个类」即可；PECS 能认出方向（读用 extends、写用 super）已属超出预期。
- **对照表是词典不是教材**：每个映射点背后的差异细节，在对应小点里展开——词典只保证你「不迷路」。

## 常见面试题

### Q1：Spring 的 IoC 是什么？和直接 new 对象有什么本质区别？

**答**：IoC（Inversion of Control，控制反转）指对象的创建、装配、生命周期管理从应用代码转移到容器。标准答案三句话：① 控制——谁来创建对象，从「开发者 new」反转为「容器统一管理」；② 反转的手段主要是 DI（依赖注入），对象只声明需要什么（构造器参数），容器负责递进来；③ 收益是解耦与可测——依赖面向接口声明，测试时注入 Mock、生产时注入实现，替换零成本。原理层的加分点：IoC 容器本质是一个「Bean 注册表 + 依赖图」，启动时按 BeanDefinition 递归实例化、解决循环依赖（三级缓存）、通过反射或字节码增强织入 AOP 代理。工程层的典型体现：singleton Bean 全容器共享一份——这正是「有状态 Bean 会被并发访问」竞态问题的源头（见[迁移心智陷阱清单](04-迁移心智陷阱清单.md)陷阱五）。

### Q2：`@Transactional` 在哪些情况下会失效？

**答**：核心结论：`@Transactional` 是代理对象上的环绕切面 + ThreadLocal 绑定的事务上下文，任何「调用没经过代理」或「执行换了线程」的写法都失效。五大经典场景：① 同类自调用（`this.methodB()` 走原始对象，绕过代理——最高频）；② 非 public 方法（代理默认只拦截 public）；③ 异常被 try-catch 吞掉（切面看不到异常，照常提交）；④ 受检异常默认不回滚（默认只回滚 RuntimeException 与 Error，需 `rollbackFor` 显式声明）；⑤ 事务方法内开新线程执行数据库操作（事务上下文绑定在 ThreadLocal，新线程拿不到）。原理层：Spring 通过 AOP 为 Bean 生成代理（JDK 动态代理或 CGLIB 子类代理），事务逻辑在代理的环绕通知里开/提交/回滚事务。工程层：生产上排查「事务没回滚」类工单，第一反应就是查这五个场景，其中自调用占比最高——解法首选拆类，而不是用 `AopContext.currentProxy()` 之类的技巧。

### Q3：NestJS 的依赖注入和 Spring 的实现原理有什么异同？

**答**：标准答案：心智同构、机制不同源——NestJS 依赖 TS 装饰器 + `reflect-metadata` 在运行期读元数据完成装配，本质也是 IoC 容器 + 依赖扫描；Spring 用注解（元数据）+ 反射 + 字节码增强（CGLIB）实现，外加三级缓存解决循环依赖、BeanPostProcessor 扩展点、代理体系支撑 AOP。原理层的三个差异：① 装配方式——NestJS 在 `@Module` 的 providers 里显式注册，Spring 用 `@ComponentScan` 类路径隐式扫描（大型工程里「这个 Bean 为什么存在」的可追溯性差异由此而来）；② 代理能力——Spring 的 AOP 是一等公民（事务、缓存、安全全靠它），NestJS 的中间件/Guard/Interceptor 是洋葱模型，没有「代理自调用失效」这类问题；③ 生命周期——Spring 的 Bean 生命周期钩子（`@PostConstruct` → init → `@PreDestroy`）比 NestJS 的 `onModuleInit` 系列更细。工程层：迁移者最需要警惕的是把 NestJS「声明即生效」的装饰器直觉套到注解上——注解只是标记，行为取决于「读它的框架代码」（见[迁移心智陷阱清单](04-迁移心智陷阱清单.md)陷阱四）。
