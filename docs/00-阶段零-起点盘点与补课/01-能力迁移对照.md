# 阶段零 · 小点 1：能力迁移对照

> 所属：阶段零 起点盘点与补课
> 定位：在正式开始前，先盘点你的既有能力对 Java 后端学习的直接迁移。这一阶段预计 1-2 周，目标是「环境就绪、路径清晰」。核心结论：你的前端 / Node / Go 经验对 Java 学习的迁移价值远比想象中大——但迁移的是**心智模型**，重学的是**语法与生态**。

## 快速入门

> 本节为「进入 Java 前的热身」：先用你熟悉的前端 / Node / Go 心智，快速认识 Java 后端整套生态长什么样、和你已有的东西如何对应。

### 本阶段核心概念速查

| 概念 | 一句话大白话 | 和你已有的对应 |
|-|-|-|
| Java 后端生态 | 一套「用 Java 写服务器」的软件家族（Spring 全家桶） | 类似 Node 的 Express/NestJS 生态 |
| JVM（Java 虚拟机） | 跑 Java 程序的「引擎」，负责把字节码变成机器码执行 | 类比 Node 的 V8 引擎 |
| Spring 框架 | Java 后端事实标准，负责对象管理、数据库、接口、安全 | 类比 NestJS 框架 |
| Maven | Java 的包管理 + 构建工具 | 类比 npm + vite 打包 |
| 注解（Annotation） | 写在类/方法上的标签，告诉框架做什么 | 类比 TS 的装饰器 |
| 依赖注入（DI） | 框架把依赖「递」给你，你不用自己 new | 与 NestJS 的 DI 同源 |
| 多线程 / 并发 | 同时处理很多请求 / 任务的机制 | 类比 Go 的 goroutine、Node 的事件循环 |
| 虚拟线程 | Java 新版轻量线程，能扛海量 IO 并发 | 类比 goroutine |

### 你为什么能学得快

- **心智模型是通用的**：依赖注入、装饰器、模块化、异步、并发——这些概念你在 NestJS / Node / Go 里都见过，Java 只是换了一套语法皮肤。
- **要重学的只有两样**：① Java 语法与标准库；② Spring 生态的工具用法（注解、配置、规范）。心智通了，剩下的都是记忆。
- **你真正需要警惕的三个「直觉陷阱」**（正文展开）：把 Promise 当 CompletableFuture、把事件循环当线程模型、把 TS 装饰器当运行时机制——这几处思维对不上，容易写出「看似对、跑起来错」的代码。

### 2. 同构代码对照：NestJS vs Spring

**依赖注入**——同一个「把依赖的创建交给框架」的心智，两种语法皮肤：

```typescript
// NestJS: @Injectable 声明可注入，构造器注入
@Injectable()
export class OrderService {
  constructor(
    private readonly repo: OrderRepository,   // 框架自动装配
  ) {}

  async create(dto: CreateOrderDto) {
    return this.repo.save(dto);
  }
}
```

```java
// Spring: @Service 声明可注入，构造器注入（单构造器可省 @Autowired）
@Service
public class OrderService {

    private final OrderRepository repo;        // 框架自动装配

    public OrderService(OrderRepository repo) { // Spring 5 起推荐构造器注入
        this.repo = repo;                      // 字段可 final —— 不可变、便于测试
    }

    public Order create(CreateOrderDto dto) {
        return repo.save(dto);
    }
}
```

> 读到这段你应该有底气了：**NestJS 的装饰器体系本来就是照着 Spring 设计的**。`@Injectable()` ≈ `@Service`，`@Module` ≈ `@Configuration + @ComponentScan`，Pipe ≈ Bean Validation。迁移成本主要在「名字对不上」，不在「概念想不通」。

**装饰器路由 vs 注解路由**：

```typescript
@Controller('orders')
export class OrderController {
  @Post()
  @UseGuards(AdminGuard)                 // Guard: 守卫
  create(@Body() dto: CreateOrderDto) { /* ... */ }
}
```

```java
@RestController
@RequestMapping("/orders")
public class OrderController {

    @PostMapping
    @PreAuthorize("hasRole('ADMIN')")    // 方法级安全 ≈ Guard
    public Order create(@Valid @RequestBody CreateOrderDto dto) { /* ... */ }
    // @Valid 触发 Bean Validation ≈ Pipe 校验
}
```

### 3. 迁移学习法的总原则与两个「直觉陷阱」

- **概念映射，语法重学**：心智模型直接复用，API 与注解体系重建肌肉记忆——用第 2 节的对照表做「翻译词典」。
- **对比 happens-before**：Go 的「不要以共享内存来通信」直觉可迁移，但 Java 的 JMM 是显式规范（阶段一第 5 讲展开）。
- **陷阱一：把 `Promise` 微任务语义套到 `CompletableFuture`**——Java 没有「事件循环兜底」，不指定执行器就走公共 ForkJoinPool，IO 任务会饿死它（阶段一第 7 讲）。
- **陷阱二：把 goroutine 的成本模型套到平台线程**——Go 开一万个 goroutine 毫无压力；Java 平台线程是重资源必须池化，虚拟线程（JDK 21+）才是对标物。

## 坑点提醒

- **别跳过阶段一直奔 Spring**：「NestJS 都会了 Spring 还难吗」的错觉，会栽在 `@Transactional` 失效、类加载、泛型擦除这些底层机制上——Spring 的「魔法」全部构建在阶段一第 3 讲（反射 / 动态代理）之上。`@Transactional` 失效的最小复现是**同类自调用**——调用绕过了代理对象，注解形同虚设：

    ```java
    public void methodA() {              // 外部经代理调用进来
        this.methodB();                  // ❌ this 是原始对象, 绕过代理 → 事务不生效
    }
    @Transactional
    public void methodB() { /* 写库 */ } // 注解形同虚设
    ```
- **别用 JS 的「动态类型」直觉读 Java 泛型**：类型擦除意味着运行时 `List<String>` 与 `List<Integer>` 是同一个类，与 TS 的「类型在编译后消失但开发期全程护航」体感相似，但通配符 PECS 是 TS 没有的深水区。
- **对照表是词典不是教材**：每个映射点背后的差异细节，在对应小点里展开——词典只保证你「不迷路」。
